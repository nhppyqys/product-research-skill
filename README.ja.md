# Product Research Skill

**ソフトウェア製品の URL を AI エージェントに渡すと、そのまま意思決定に使えるレポートが返ってくる。**

[English](README.md) · [简体中文](README.zh-CN.md) · MIT

---

## これは何か

AI エージェント向けの調査メソッドと、それを強制するチェッカーです。

エージェントに URL を渡すと、固定された 10 ステップを順に実行します——サイトの棚卸し、レンダリング後の価格ページ読み取り、トップページの主張を一つずつ証拠と突き合わせ、本当の競合を洗い出し、日付つきの逐語レビューを収集し、直近 30 日の変化を確認する。そして**要約ではなく、提言で終わるレポート**を書きます。

**調査対象はインターネットのソフトウェア製品です**：SaaS ツール、モバイル／Web アプリ、開発者ツールと API、オープンソースプロジェクト、マーケットプレイス。**ウェブサイトがあり、価格ページがあり、ユーザーが公の場で不満を書く**もの。

**対象外**：物理商品、株式、地域のビジネス、個人。このメソッドが依拠する証拠経路——価格ページ、ドキュメント、アプリストア、レビューサイト、リポジトリ——は、ソフトウェア製品にしか存在しません。

## 何が得られるか

5 つの問いに、この順で答えるレポート：

1. **これは結局何なのか？** API エンドポイントの羅列ではなく「何を解決するか」で記述した機能モジュール、そして実 UI のスクリーンショット
2. **どうやって稼いでいるのか？** 全プラン、実際に従量課金される対象、最上位プランに閉じ込められている機能、そして**価格ページに載っていない割引**
3. **この会社は実在するのか？** 設立年、拠点、人数、調達額、売上——各項目に出典、または明示的な「調査したが見つからず」
4. **他に誰がやっていて、どの位置にいるのか？** 比較の前にまず階層化し、用いた指標とその歪みの方向を明記
5. **利用者は実際どう言っているのか？** 出典・日付・属性つきの逐語引用 10 件以内——**評判は時間とともに変わるため、時系列でグループ化**

そして**あなたの意思決定のために書かれた判断**と、「何が取得できず、それがどの結論を弱めるか」を述べた境界セクション。

## 誰のためのものか

| あなたが | 使いどころ |
|---|---|
| **ソフトを買う立場** | 課金単位の異なるツールを揃えて実コストを比較し、契約前に不満を把握し、何を交渉すべきかを知る |
| **プロダクトを作る立場** | そのカテゴリに既に誰がいるかを把握し、誰も埋めていない空白を見つけ、資本効率からその市場が儲かるのかを見る |
| **投資する立場** | 収益の質、資本効率、流通構造、堀の証拠を確認し、どの数字を検証し直すべきかを見極める |
| **プロダクトを運営する立場** | 競合の機能アーキテクチャ、ユーザージャーニー、摩擦点、リリース頻度を分解する |

**エージェントに「この製品を分析して」と頼んでトップページの言い換えが返ってきた経験があるなら、これはその修正です。**

## クイックスタート

インストール不要、API キー不要。エージェントが読める場所にファイルを置くだけ：

```bash
git clone https://github.com/nhppyqys/product-research-skill
cp -r product-research-skill/skills/product-research ~/.claude/skills/
```

そして：

```
product_research_method を使って https://example.com を購買担当の視点で調査して
```

エントリのメソッドが、必要なステップで必要なサブメソッドを自分で読み込みます。誰かに渡す前に：

```bash
node scripts/check-report.mjs report.md
```

ローカルファイルを読めてウェブを閲覧できるエージェントなら何でも動きます。**特定フレームワークに依存する要素はありません。**

## なぜレポートが違うのか

このメソッドは、実在する製品で同じ調査を何度も回し、**失敗するたびに原因を書き留め、失敗を一つずつルールに変えて**作られました。**42 件の失敗**が記録され、それぞれに「このルールが成立しなくなる条件」が併記されています。

その結果、多くの調査が見落とす技術が生まれました：

**404 ページに会社の従業員数が載っていることがある。** SEO プラグインは `schema.org` の組織情報を **404 を含むすべての**ページテンプレートに注入します。存在しないパスを叩いて構造化データを読むだけで、従業員数レンジ・設立年・拠点都市・公式ポジショニング文が一度のリクエストで手に入ることがある。→ [C-02](skills/product-research/casebook.md)

**`robots.txt` は多くのサイトで最も情報密度が高いファイル。** `Disallow` に並ぶのは「検索エンジンに見せたくないもの」——割引ランディングページ、チャネル別価格、トライアル導線。ある製品は公開価格を月 45〜329 ドルと表示しながら「初月 77% off」「年払い 500 ドル引き」の 2 ページを隠していた。**表示価格は成約価格ではなかった。**→ [C-03](skills/product-research/casebook.md)

**ログインウォールは壁ではない。** ベンダー自身のチュートリアル動画は実 UI の画面録画です——録画しなければ教えられないので当然そうなる。**公式サイトにもドキュメントにも一切記載のない MCP 機能**が、別々の 2 製品でデモ動画からのみ見つかりました。→ [C-05](skills/product-research/casebook.md)

**価格ページのスクレイプが空でも、たいてい本当に空ではない。** 価格はスクリプトで描画されるのが一般的です。ある報告はそれを根拠に「ログインしないと価格が見えない」と書いたが、ブラウザで開くと 7 段階すべてが明示されていた。**「取得できなかった」は「提供されていない」ではない。**→ [C-04](skills/product-research/casebook.md)

**オープンコア製品では、課金の境界線はディレクトリそのもの。** `LICENSE` に商用ライセンス配下のフォルダ名が明記されている——それが有料機能リストであり、ベンダーが曖昧にできない言葉で書かれています。**ライセンス変更は通常のコミットに紛れ込む**：ある製品は 670 行の AGPL + 商用条項を 21 行の MIT に差し替えたが、それは `refactor:` という題の 300 ファイル変更コミットの中でした。→ [C-32, C-34](skills/product-research/casebook.md)

**マーケットプレイスでは `/pricing` が出品者のものかもしれない。** トップレベルの名前空間が出品者ストアに落ちることがある。`/pricing` も `/security` も 200 を返したが、一方は「PRICING」という名の店舗、もう一方は「Oracle's store」でした。**ステータスコードでは区別できません。**→ [C-38](skills/product-research/casebook.md)

## 仕組み

4 つの部品が、それぞれ 1 つの役割だけを持ちます：

```
 skills/product-research/
 ├── product-research-method.md   やり方    — 10 ステップ + 製品形態別の分岐
 ├── casebook.md                  なぜ      — 42 件の実測ケース、各々に境界つき
 ├── contract.json                足りたか  — 20 の完了基準、機械可読
 └──（4 つのサブメソッド）                  視点 · 競合環境 · 利用者の声 · 直近の変化
        │
        ▼
 scripts/check-report.mjs         強制      — 納品前に契約を実行する
```

**互いに重複しません。**メソッドに数値は書かない（数値は契約に）。契約に理由は書かない（理由はケースブックに）。基準を変えるなら契約、やり方を変えるならメソッド、学びを足すならケースブック。

**ルーティングは決定的**：キーワードで到達できるのはエントリのメソッドだけで、4 つのサブメソッドは**指定ステップで名指しで読み込まれます**。パックにエントリがちょうど 1 つでなければビルドが失敗します。

### チェックリストではなく契約にした理由

メソッドには約 63 のセクションに散らばった約 69 個の必須要件があります。**長い文書の末尾に置かれたチェックリストは実行されません。**実測済みです：

| 抜け落ちたもの | 期間 |
|---|---|
| スクリーンショット（「環境がレンダリングできない」） | 5 ラウンド — 実際はできた。誰も試していなかっただけ |
| 直近 30 日の変化 | 3 ラウンド — サブメソッドは存在したが、呼び出すステップが無かった |
| 市場の階層分析 | 一度やって消えた — フローに入っていなかった |
| 「主張 vs 事実」セクション丸ごと | 1 ラウンド。書いた本人もレビューも気づかず |

最後の 1 件を見つけたのは**チェッカー**であって人ではありません。**散文には強制力がなく、コードにはある。**

完成したレポートからは読み取れない要件もあります——いくつのパスを叩いたか、いくつの事例を読んだか、動画チャンネルを見たか。これらは[エビデンス・マニフェスト](docs/evidence-manifest.md)という別ファイルに置き、**レポートには同梱しません**。

ステップを飛ばすには 3 つの理由のいずれかが必要で、それ以外は認められません：

| 理由 | 意味 |
|---|---|
| `blocked` | フォールバック経路を全て試して失敗 — どれを試し、何が返ったかを明記 |
| `absent` | 対象が存在しない（モバイルアプリが無ければアプリストアのレビューも無い） |
| `incapable` | 環境が本当にできない — **実際に試した上で、エラー文を引用すること** |

`incapable` にこの但し書きが付いているのは、**5 ラウンド連続で乱用されたから**です。

## ケースブックが他と違う点

各ケースには 7 つの欄があり、そのうち 2 つが本質です：

- **前提** — どんな形態の製品で、どんな条件下か。*目の前の製品にこのケースが当てはまるかを決めます。*
- **当てはまらない場合** — このルールに従うと、かえって悪化する状況。

**この 2 欄を欠いたケースは、ケースが無いより危険です。**条件を伴わない結論を渡すことになり、無関係な仕事に事実として持ち込まれます。

理屈ではありません：クロスモデル検証で、モデルが**まったく別の製品**のレポートに「顧客事例ページが無い（`/customers` は 404）」と書きました——メソッド文書中の例からの持ち出しで、3 回中 2 回再現。→ [C-28](skills/product-research/casebook.md)

## クロスモデル検証の結果

同じメソッド・同じ証拠で、2 モデル各 3 回：

| | 結論 | 失敗の仕方 | コードで防げるか |
|---|---|---|---|
| **速いモデル** | 3/3 正しい | フォーマット：インライン HTML、会話的な前置き、バージョン文字列の漏洩 | **防げる** |
| **遅いモデル** | 正しく、文章も上手い | **3 回中 2 回で証拠を捏造**；3 回とも内部用語が漏洩 | **防げない** |

遅いモデルはより良い文章を書き、同時に**一度も観測していないステータスコードを創作しました**。**どちらもノーチェックで走らせてはいけません。**実用的な構成は、速いモデル + 必須チェッカーです。

## カバー範囲と、薄いところ

**完全性を主張するより、較正済みの範囲を正直に示すほうが重要です：**

| 製品形態 | 実測サンプル | 未カバー |
|---|---|---|
| セルフサーブ SaaS | 4 | — |
| エンタープライズ営業 | 2 | クラウドマーケットプレイスの契約価格 |
| コンシューマーアプリ | 1 | ランキング順位、広告出稿シグナル |
| 開発者ツール / API | 2 | レート制限とエラーコードの完全な分解 |
| アーリーステージ（レビューも事例も無い） | 1 | — |
| オープンソース / オープンコア | 1 | **今もオープンコアである**サンプルが無い — 対象は完全 MIT 化済み |
| マーケットプレイス / two-sided | 1 | 出店ルール；**需要側は本質的に測定不能**（未検証ではなく） |

未検証の形態でこのメソッドを回すこと自体は問題ありません。**較正済みのふりをするのが問題**です——レポートの「境界」セクションに明記してください。

## 現状

メソッド自体は安定しています——6 つの形態の製品でエンドツーエンドに実行済みです。未完了の点が 2 つ：

- **メソッド本体は英語のみ。これは意図的です。**4 万トークン規模のメソッドを複数言語で同期し続けるのは無理があり、実際に一度ズレました。ドキュメントと README は 3 言語、メソッド自体は真実の源をひとつに保ちます。
- **レポートのブランディングはオプトイン**（`assets/report-header.md` と `BRAND_HEADER` 変数）。デフォルトはブランド無しです。

## コントリビュート

最も価値ある貢献は**ケース**です。カバー表で薄いとされた形態でメソッドを回し、うまくいかなかった点を 7 欄形式で書いてください——**「当てはまらない場合」の欄を必ず含めること。**境界の無いケースはマージされません。

チェッカーのバグ報告も歓迎します。**特に誤検知**を。狼少年になったチェッカーは無視されるようになり、無視されるチェッカーは無いより悪いからです。
