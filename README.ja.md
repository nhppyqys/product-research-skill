# Product Research Skill

**AI エージェント向けのプロダクト調査メソッド。購買担当・起業家・投資家がそのまま judgment に使えるレポートを出す — 完了基準はコードが強制し、善意に頼らない。**

[English](README.md) · [简体中文](README.zh-CN.md)

---

エージェントに「このプロダクトを分析して」と頼むと、たいていトップページの要約が返ってくる。このメソッドは、それが起きないようにするためのものです。

実在するプロダクトで同じ調査を何度も回し、**失敗するたびにその原因を書き留め、失敗を一つずつルールに変えて**積み上げました。ここには **42 件の失敗**が記録されていて、それぞれに「このルールが成立しなくなる条件」が併記されています。

## このメソッドが知っていて、たいてい見落とされること

以下はすべてケースブックにある実測テクニックで、想定ではありません。

**404 ページに会社の従業員数が載っていることがある。**SEO プラグインは `schema.org` の Organization JSON-LD を **404 を含むすべての**ページテンプレートに注入します。存在しないパスを叩いてその JSON-LD を読むだけで、従業員数レンジ・設立年・拠点都市・公式ポジショニング文が一度のリクエストで手に入ることがある。→ [C-02](skills/product-research/casebook.md)

**`robots.txt` は多くのサイトで最も情報密度が高いファイル。**`Disallow` に並ぶのは「検索エンジンに見せたくないもの」——割引ランディングページ、チャネル別価格、トライアル導線。ある製品は公開価格を月 45〜329 ドルと表示しながら、`/offer/…-77-off-first-month` と `/offer/…-500-off-annually` を隠していた。**表示価格は成約価格ではなかった。**→ [C-03](skills/product-research/casebook.md)

**ログインウォールは壁ではない。**ベンダー自身のチュートリアル動画は実 UI の画面録画です——録画しなければ教えられないので当然そうなる。`yt-dlp` でチャンネルを取り、`ffmpeg` でフレームを抜く。**公式サイトにもドキュメントにも一切記載のない MCP 機能**が、別々の 2 製品でデモ動画からのみ見つかりました。→ [C-05](skills/product-research/casebook.md)

**オープンコア製品では、課金の境界線はディレクトリそのもの。**`LICENSE` ファイルに商用ライセンス配下のフォルダ名が明記されている——それが有料機能リストであり、ベンダーが曖昧にできない言葉で書かれています。**ライセンス変更は通常のコミットに紛れ込む**：ある製品は 670 行の AGPL + 商用条項を 21 行の MIT に差し替えたが、それは `refactor:` という題の 300 ファイル変更コミットの中でした。→ [C-32, C-34](skills/product-research/casebook.md)

**マーケットプレイスでは `/pricing` が出品者のものかもしれない。**two-sided プラットフォームではトップレベルの名前空間が出品者ストアに落ちることがある。`/pricing` も `/security` も 200 を返したが、一方は「PRICING」という名の店舗、もう一方は「Oracle's store」でした。**ステータスコードでは区別できません。**→ [C-38](skills/product-research/casebook.md)

**供給側の速度は測れるが、需要側はたいてい測れない。**出品一覧は sitemap に無くても「新着」RSS にはタイムスタンプがある：100 件が 316 分に分布 ≒ **1 日あたり約 455 件の新規出品**。買い手は公開痕跡を残さないので、サイト全体のトラフィックを買い手規模に見せかけるのではなく、**測れないと明言する**のが誠実なやり方です。→ [C-39, C-42](skills/product-research/casebook.md)

## クイックスタート

インストール不要、API キー不要。エージェントが読める場所にファイルを置くだけ：

```bash
git clone https://github.com/nhppyqys/product-research-skill
cp -r product-research-skill/skills/product-research/ ~/.claude/skills/
```

そして：

```
product_research_method を使って https://example.com を購買担当の視点で調査して
```

以上です。エントリのメソッドが、必要なステップで必要なサブメソッドを自分で読み込みます。

誰かに渡す前に：

```bash
node scripts/check-report.mjs report.md
```

## 何が出てくるか

デモ用ではなく、**意思決定のために構成された**レポート：

```
まず読む部分    専門用語なし。何で、誰が買い、いくら稼ぎ、どの位置にいて、最大のリスクは何か
これは何か      ビジネス言語での機能モジュール + 実 UI スクリーンショット
価格            プラン、課金単位、実際に従量課金されるもの、
                そして robots.txt に隠れていた割引
主張 vs 事実    トップページの主張を一つずつ 成立 / 不成立 / 検証不能 で判定
会社            設立・本社・創業者・調達・従業員数・売上・評価額
競合環境        まず階層に分け、それから比較する。階層をまたいだ比較はしない。
利用者の声      出典・日付・属性つきの逐語引用 10 件以内 —
                評判は時間とともに変わるので、時系列でグループ化する
リスク
判断            視点ごとに分ける：購買 / 起業 / 投資 / PM
境界            何が取得できなかったか → それが結論をどう弱めるか
```

**最後のセクションが最も重要です。**書くべきは「X が取れなかったので結論 Y は弱い」であって、「X をやっていない」ではありません。前者はプロの仕事、後者は言い訳です。

## 仕組み

4 つの部品が、それぞれ 1 つの役割だけを持ちます：

```
 skills/product-research/
 ├── product-research-method.md   やり方    — 10 ステップ + 形態別の分岐
 ├── casebook.md                  なぜ      — 42 件の実測ケース、各々に境界つき
 ├── contract.json                足りたか  — 20 の完了基準、機械可読
 └──（サブメソッド）                        視点 · 競合環境 · 利用者の声 · 直近の変化
        │
        ▼
 scripts/check-report.mjs         強制      — 納品前に契約を実行する
```

**互いに重複しません。**メソッドに数値は書かない（数値は契約に）。契約に理由は書かない（理由はケースブックに）。基準を変えるなら契約、やり方を変えるならメソッド、学びを足すならケースブック。

**ルーティングは決定的です。**キーワードで到達できるのはエントリのメソッドだけ。4 つのサブメソッドは trigger が空で、**指定ステップで名指しで読み込まれます**。パックにエントリがちょうど 1 つでなければビルドが失敗します。

### チェックリストではなく契約にした理由

メソッドには約 63 のセクションに散らばった約 69 個の必須要件があります。**長い文書の末尾に置かれたチェックリストは実行されません。**実測済みです：

| 抜け落ちたもの | 期間 |
|---|---|
| スクリーンショット（「環境がレンダリングできない」） | 5 ラウンド — 実際はできた。誰も試していなかっただけ |
| 直近 30 日の変化 | 3 ラウンド — サブメソッドは存在したが、呼び出すステップが無かった |
| 市場の階層分析 | 一度やって消えた — フローに入っていなかった |
| 「主張 vs 事実」セクション丸ごと | 1 ラウンド。書いた本人もレビューも気づかず |

最後の 1 件を見つけたのは**チェッカー**であって人ではありません。**散文には強制力がなく、コードにはある。**

完成したレポートからは読み取れない要件もあります——いくつのパスを叩いたか、いくつの事例を読んだか、ベンダーの動画チャンネルを見たか。これらは[エビデンス・マニフェスト](docs/evidence-manifest.md)という別ファイルに置き、**レポートには同梱しません**。

ステップを飛ばすには 3 つの理由のいずれかが必要で、それ以外は認められません：

| 理由 | 意味 |
|---|---|
| `blocked` | フォールバック経路を全て試して失敗 — どれを試し、何が返ったかを明記 |
| `absent` | 対象が存在しない（モバイルアプリが無ければアプリストアのレビューも無い） |
| `incapable` | 環境が本当にできない — **実際に試した上で、エラー文を引用すること** |

`incapable` にこの但し書きが付いているのは、**5 ラウンド連続で乱用されたから**です。

## ケースブックが他と違う点

各ケースには 7 つの欄があり、そのうち 2 つが本質です：

- **前提** — どんな形態の製品で、どんな条件下か。*目の前の製品にこのケースが当てはまるかを決めます。*
- **当てはまらない場合** — このルールに従うと、かえって悪化する状況。

**この 2 欄を欠いたケースは、ケースが無いより危険です。**条件を伴わない具体的な結論を渡すことになり、無関係な仕事に事実として持ち込まれます。

これは理屈ではありません。クロスモデル検証で、モデルが**まったく別の製品**のレポートに「顧客事例ページが無い（`/customers` は 404）」と書きました——メソッド文書中の例からの持ち出しで、3 回中 2 回再現しました。→ [C-28](skills/product-research/casebook.md)

## クロスモデル検証の結果

同じメソッド・同じ証拠で、2 モデル各 3 回：

| | 結論 | 失敗の仕方 | コードで防げるか |
|---|---|---|---|
| **速いモデル** | 3/3 正しい | フォーマット：インライン HTML、会話的な前置き、バージョン文字列の漏洩 | **防げる** |
| **遅いモデル** | 正しく、文章も上手い | **3 回中 2 回で証拠を捏造**；3 回とも内部用語が漏洩 | **防げない** |

遅いモデルはより良い文章を書き、同時に**一度も観測していないステータスコードを創作しました**。**どちらもノーチェックで走らせてはいけません。**実用的な構成は、速いモデル + 必須チェッカーです。

## カバー範囲と、薄いところ

**完全性を主張するより、較正済みの範囲を正直に示すほうが重要です：**

| 製品形態 | 実測サンプル | 未カバー |
|---|---|---|
| セルフサーブ SaaS | 4 | — |
| エンタープライズ営業 | 2 | クラウドマーケットプレイスの契約価格 |
| コンシューマーアプリ | 1 | ランキング順位、広告出稿シグナル |
| 開発者ツール / API | 2 | レート制限とエラーコードの完全な分解 |
| アーリーステージ（レビューも事例も無い） | 1 | — |
| オープンソース / オープンコア | 1 | **今もオープンコアである**サンプルが無い — 対象は既に完全 MIT 化済み |
| マーケットプレイス / two-sided | 1 | 出店・審査ルール；**需要側は本質的に測定不能**（未検証ではなく） |

未検証の形態でこのメソッドを回すこと自体は問題ありません。**較正済みのふりをするのが問題**です——レポートの「境界」セクションに明記してください。

## コントリビュート

最も価値ある貢献は**ケース**です。カバー表で薄いとされた形態でメソッドを回し、うまくいかなかった点を 7 欄形式で書いてください——**「当てはまらない場合」の欄を必ず含めること。**境界の無いケースはマージされません。

チェッカーのバグ報告も歓迎します。**特に誤検知**を。狼少年になったチェッカーは無視されるようになり、無視されるチェッカーは無いより悪いからです。
