# Product Research Skill

**给 AI 代理用的产品调研方法。产出的是采购、创业、投资三种人能直接拿去做决定的报告——完成标准由代码执行，不靠自觉。**

[English](README.md) · [日本語](README.ja.md)

---

让代理"分析一下这个产品"，多半会得到一份首页摘要。这套方法是为了让这件事不再发生。

它是在真实产品上反复跑同一套流程、把每一次做错的地方记下来、再把每次失败变成一条规则攒出来的。**这里记了 42 次失败**，每一条都写清了这条规则在什么情况下不再成立。

## 这套方法知道、而大多数人不知道的事

以下都是案例库里的真实技术，不是设想：

**404 页面上常常挂着公司的人数。**SEO 插件会把 `schema.org` 的 Organization JSON-LD 注入**每一个**页面模板，包括 404。探一个不存在的路径、读那段 JSON-LD，一次请求就可能拿到员工区间、成立年份、办公室城市和官方定位文案。→ [C-02](skills/product-research/casebook.md)

**`robots.txt` 是多数站点上信息密度最高的文件。**它的 `Disallow` 清单就是这家公司不想被搜索引擎看到的东西：折扣落地页、按渠道定制的报价、试用漏斗。某产品官网明码标价 45–329 美元，同时藏着 `/offer/…-77-off-first-month` 和 `/offer/…-500-off-annually`——**标价从来不是成交价。**→ [C-03](skills/product-research/casebook.md)

**登录墙不是墙。**厂商自己的教学视频就是真实界面的录屏——不录屏没法教人。`yt-dlp` 拉频道，`ffmpeg` 抽帧。两个不同的产品都被挖出**官网和文档里一个字都没提的 MCP 能力**，只在演示视频里出现过。→ [C-05](skills/product-research/casebook.md)

**开放核心产品的付费墙就是一个目录。**`LICENSE` 文件里写明了哪几个文件夹走商业授权——那就是付费功能清单，而且是厂商无法含糊其辞的措辞。**许可证变更还会藏在普通提交里**：某产品把 670 行的 AGPL + 商业条款换成 21 行 MIT，就发生在一个标题为 `refactor:` 的 300 文件提交中。→ [C-32、C-34](skills/product-research/casebook.md)

**双边市场的 `/pricing` 可能属于某个卖家。**平台的顶级命名空间常常落到店铺上。`/pricing` 和 `/security` 都返回 200——一个是名叫 "PRICING" 的店铺，另一个是 "Oracle's store"。**状态码分不出来。**→ [C-38](skills/product-research/casebook.md)

**供给侧速率可测，需求侧通常不可测。**卖家列表不在 sitemap 里，但"最新上架"RSS 带时间戳：100 条跨 316 分钟 ≈ 每天 455 个新商品。买家不留公开痕迹，所以诚实的做法是直接说明，而不是拿整站流量冒充买家规模。→ [C-39、C-42](skills/product-research/casebook.md)

## 快速上手

不用装东西，不用 API key。把方法文件放到代理能读到的地方：

```bash
git clone https://github.com/nhppyqys/product-research-skill
cp -r product-research-skill/skills/product-research ~/.claude/skills/
```

然后：

```
用 product_research_method 调研 https://example.com，视角是采购者
```

就这样。入口方法会在需要的步骤自己拉取需要的子方法。

交给别人之前：

```bash
node scripts/check-report.mjs 报告.md
```

## 产出长什么样

报告是按决策组织的，不是按演示组织的：

```
先读这段        不用术语。是什么、卖给谁、赚多少钱、什么位置、最大风险
它是什么        业务语言的功能模块 + 真实界面截图
怎么收费        档位、计价单位、真正计量的是什么，
                以及 robots.txt 里藏着的折扣
宣称与事实      每条首页宣称逐条标 成立 / 不成立 / 无法核实
公司            成立、总部、创始人、融资、员工、收入、估值
赛道            先分层再比较。绝不跨层比。
用户怎么说      ≤10 条逐字引文，带来源、日期、身份——
                按时间分组，因为口碑会漂移
风险
判断            按视角拆开：采购者 / 创业者 / 投资人 / 产品经理
边界            未取得什么 → 以及这对结论构成什么限制
```

**最后一节最重要。**它写的是"没拿到 X，所以结论 Y 更弱"，不是"我没做 X"。前者是专业，后者是免责。

## 怎么工作

四个部件，各管一件事：

```
 skills/product-research/
 ├── product-research-method.md   怎么做  — 10 步顺序 + 按形态分岔
 ├── casebook.md                  为什么  — 42 条实测案例，每条带边界
 ├── contract.json                够没够  — 20 条完成标准，机器可读
 └── （子方法）                            视角 · 赛道 · 口碑 · 近期变化
        │
        ▼
 scripts/check-report.mjs         执行    — 交付前跑一遍契约
```

**四者不重复。**方法里不写数字（数字在契约），契约里不讲道理（道理在案例库）。改标准改契约，改做法改方法，加教训加案例库。

**路由是确定的。**只有入口方法能被关键词命中，四个子方法的触发词全部为空，**由入口在指定步骤点名加载**。一个包里不是恰好一个入口，构建直接失败。

### 为什么用契约，不用清单

方法里有约 69 处硬性要求，散落在约 63 个章节。**放在长文档末尾的自检清单不会被执行**——这是实测出来的：

| 漏掉了什么 | 漏了多久 |
|---|---|
| 截图（"环境无渲染能力"） | 5 轮——环境其实可以，只是没人试过 |
| 近 30 天变化 | 3 轮——子方法一直在，但没有一步调用它 |
| 赛道分层分析 | 做过一次就消失了——它从来没进过流程 |
| 整节"宣称与事实" | 1 轮，作者和评审都没发现 |

最后那条是**检查器**发现的，不是人。**散文没有执行力，代码有。**

有些要求从成品报告里看不出来——探了几个路径、读了几个客户案例、有没有翻过厂商的视频频道。这些放在独立的[证据清单](docs/evidence-manifest.md)里，**不随报告交付**。

跳过某一步只认三个理由，别的一律不算：

| 理由 | 含义 |
|---|---|
| `blocked` | 降级通道全部试过并失败——写明试了哪几个、各报什么错 |
| `absent` | 对象不存在（没有移动端就没有应用商店评论） |
| `incapable` | 环境确实做不到——**必须真的试过，并附上报错原文** |

`incapable` 之所以带这句警告，是因为它被连续滥用了五轮。

## 案例库为什么不一样

每条案例有七栏，其中两栏才是关键：

- **前提**——什么形态的产品、什么条件下成立。*它决定这条案例适不适用于你眼前这个产品。*
- **不适用于**——照这条规则做反而会更糟的情况。

**缺这两栏的案例比没有案例更危险。**它给你一个具体结论，却不给你这个结论成立的条件，于是被当成通用事实带进不相干的工作里。

这不是假设。跨模型测试中，模型在一份**完全无关**的报告里写下了"没有客户案例页（`/customers` 返回 404）"——那句话是从方法文档的举例里搬来的，3 轮里复现 2 轮。→ [C-28](skills/product-research/casebook.md)

## 跨模型实测结果

同一套方法、同一份证据，两个模型各跑三轮：

| | 结论 | 失败方式 | 代码能兜住吗 |
|---|---|---|---|
| **快模型** | 3/3 正确 | 格式问题：内联 HTML、对话式开场、泄露版本号 | **能** |
| **慢模型** | 正确，行文更好 | **3 轮中 2 轮编造证据**；3 轮全部泄露内部术语 | **不能** |

慢模型写得更好，同时也编造了一个从未观察到的状态码。**两个都不能裸跑。**实际可用的组合是快模型 + 强制检查器。

## 覆盖到哪，哪里还薄

**如实说明校准范围，比声称完整更重要：**

| 产品形态 | 实测样本 | 未覆盖 |
|---|---|---|
| 自助 SaaS | 4 | — |
| 企业销售制 | 2 | 云市场合约价 |
| 消费级应用 | 1 | 榜单位置、买量信号 |
| 开发者工具 / API | 2 | 限额与错误码的完整解剖 |
| 早期产品（无口碑无案例） | 1 | — |
| 开源 / 开放核心 | 1 | 没有**仍处于开放核心状态**的样本——我们那个已转全 MIT |
| 双边市场 | 1 | 入驻与审核规则；**需求侧本质不可测**，不是没测 |

在未实测的形态上跑这套方法没问题，**但不要假装有把握**——在报告的边界一节写明。

方法本身是稳的——已经在六种形态的产品上端到端跑通过。两件事明确未完成：

## 参与

最有价值的贡献是一条案例。挑覆盖表里标为薄弱的形态跑一遍，撞到问题就按七栏格式写下来——**必须包含"不适用于"那一栏**。缺边界的案例不会被合并。

检查器的 bug 同样欢迎，**尤其是误报**。老喊狼来了的检查器会被忽略，而被忽略的检查器比没有更糟。
