# 仕組み

[English](how-it-works.md) · [简体中文](how-it-works.zh-CN.md) · **日本語**

4 つの部品が、それぞれ 1 つの役割だけを持ちます。

```
 skills/product-research/
 ├── product-research-method.md   やり方    — 10 ステップ + 製品形態別の分岐
 ├── casebook.md                  なぜ      — 42 件の実測ケース、各々に境界つき
 ├── contract.json                足りたか  — 20 の完了基準、機械可読
 ├── research-viewpoint.md        \
 ├── market-landscape.md           |    サブメソッド。エントリが指定ステップで
 ├── customer-proof.md             |    名指しで読み込む
 └── last-30-days.md              /
        │
        ▼
 scripts/check-report.mjs         強制
```

**互いに重複しない。これが設計の全てです。**メソッドに数値は書かない（数値は契約に）。契約に理由は書かない（理由はケースブックに）。基準を変えるなら契約、やり方を変えるならメソッド、学びを足すならケースブック。**重複が無いので、手作業で同期すべきものが何もありません。**

## ルーティング

キーワードで到達できるのはエントリのメソッドだけです。**4 つのサブメソッドは trigger が空で、必要なステップでエントリが名指しで読み込みます。**

これは意図的です。すべてのファイルが trigger を持っていた頃は、3 つが「競合」を、2 つが「市場」を奪い合っていました——**同じリクエストがサブメソッドに着地し、フロー全体を迂回してしまう**。現在はパック内に `entry: true` がちょうど 1 つでなければビルドが失敗します。

```bash
node scripts/build-skills.mjs          # skills/catalog.json と dist/skills.generated.ts を生成
node scripts/build-skills.mjs --check  # CI：生成物が古ければ失敗
```

⚠️ `--check` が存在する理由：かつて埋め込まれたスキルのコピーが**ソースの 40% まで静かに切り詰められ**、段落が文の途中で切れたまま長期間動き続け、誰も気づきませんでした。

## 契約

メソッドには約 63 のセクションに散らばった約 69 個の必須要件があります。**長い文書の末尾に置かれたリストは実行されません**——4 つの要件がそれぞれ複数ラウンドにわたって欠落し、そのうち 1 つはチェッカーが発見しました。人間のレビューでは一度も見つかりませんでした。

そこで基準は散文から `contract.json` へ移され、チェッカーが実行します。20 ステップのうち：

- **12 ステップはレポート本文から自動判定**——埋め込み画像の数、日付つき引用の数、主張テーブルの行数、会社 7 項目の有無
- **8 ステップはエビデンス・マニフェストでの宣言が必要**。成果物ではなく調査プロセスを記述するため
- **3 ステップは形態専用**で、`shape` が明示的に宣言された場合のみ発火
- **1 ステップは視点専用**（階層化は起業家・投資家視点でのみ必須）

## チェッカー

```bash
node scripts/check-report.mjs report.md
```

一度に 2 種類を実行します：

**完了度**——契約をステップごとに判定し、達成 / 未達成 / 未宣言 / 免除 を出力。

**衛生**——インライン HTML、内部メソッド名、内部用語、作業ログ的な言い回し、「要検証」テーブル、未置換のプレースホルダ、例の混入。

**例の混入は意図的に「必須修正」ではなく「警告」にしてあります。**このチェックは「メソッド文書から持ち出した名前」と「今回実際に調べた名前」を区別できません——**判断できるのは人間だけです**。ハードブロックに設定していた時、あるレポートで 3 社を検出しましたが、**その 3 社はいずれもその日に取得したデータでした**。**本物の証拠を削除させるチェッカーは、防ごうとしている問題より有害です。**

ブランディングはオプトインです。`BRAND_HEADER` にレポートのヘッダーが一致すべき正規表現を設定します。未設定ならこのルールは何もしません。

## パックを追加する

```
skills/<パック名>/
├── README.md          人間向け。読み込まれない
├── <エントリ>.md      frontmatter に entry: true
└── <メンバー>.md      エントリから名指しで読み込まれる
```

frontmatter には `name`、`version`、`description` が必須。エントリにはさらに `triggers` が必要ですが、**メンバーには持たせてはいけません**——ビルドはエントリがちょうど 1 つでないパックを拒否し、メンバーは設計上キーワードで到達できません。

`description` はモデルがルーティング時に見る唯一の情報です。**「どんなリクエストがここに来るべきか」を書いてください。ファイルの中身の説明ではありません。**

`_` で始まるフォルダはビルド対象外です。アーカイブや作業中のものに使います。
