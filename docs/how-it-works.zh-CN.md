# 工作原理

[English](how-it-works.md) · **简体中文** · [日本語](how-it-works.ja.md)

四个部件，各管一件事。

```
 skills/product-research/
 ├── product-research-method.md   怎么做  — 10 步顺序 + 按产品形态分岔
 ├── casebook.md                  为什么  — 42 条实测案例，每条带边界
 ├── contract.json                够没够  — 20 条完成标准，机器可读
 ├── research-viewpoint.md        \
 ├── market-landscape.md           |     子方法，由入口在指定步骤点名加载
 ├── customer-proof.md             |
 └── last-30-days.md              /
        │
        ▼
 scripts/check-report.mjs         执行
```

**四者不重复，这就是整个设计。**方法里不写数字（数字在契约），契约里不讲道理（道理在案例库）。改标准改契约，改做法改方法，加教训加案例库。**没有任何东西需要人工同步，因为没有任何东西是重复的。**

## 路由

只有入口方法能被关键词命中。**四个子方法的触发词为空，由入口在需要它的那一步点名加载。**

这是刻意的。当每个文件都带触发词时，三个抢"竞品"、两个抢"赛道"——**同一个请求可能落到某个子方法上，绕过整套流程**。现在一个包里如果不是恰好一个 `entry: true`，构建直接失败。

```bash
node scripts/build-skills.mjs          # 生成 skills/catalog.json 与 dist/skills.generated.ts
node scripts/build-skills.mjs --check  # CI：生成物过期就失败
```

⚠️ `--check` 的来历：曾经有一份内嵌的 skill 副本**静默截断到源文件的 40%**，段落被从句子中间切断，这样跑了很久没人发现。

## 契约

方法里有约 69 处硬性要求，散落在约 63 个章节。**放在长文档末尾的清单不会被执行**——有四项要求各自漏了好几轮，其中一项是检查器发现的，人工评审从没发现。

所以标准从散文搬进了 `contract.json`，由检查器执行。20 步里：

- **12 步能从报告正文自动判定**——数嵌入的图、数带日期的引文、数宣称表的行数、查公司七项是否齐全
- **8 步需要在证据清单里声明**，因为它们描述的是调研过程而不是交付物
- **3 步是形态专用的**，只在显式声明了 `shape` 时才触发
- **1 步是视角专用的**（分层只对创业者和投资人视角要求）

## 检查器

```bash
node scripts/check-report.mjs 报告.md
```

一次跑两类：

**完成度**——按契约逐步判定，输出 达标 / 未达标 / 未声明 / 已豁免。

**卫生**——内联 HTML、内部方法名、内部术语、工作日志措辞、"待测"表、未替换的占位符、举例串味。

**举例串味是刻意设成"提醒"而不是"必修"的。**这条检查区分不了"从方法文档里抄来的名字"和"本轮真查过的名字"——**只有人能判**。当初设成硬拦截时，它在一份报告里拦下了三家公司，**而那三家的数据都是当天现拉的**。**一个逼着你删掉真实证据的检查器，比它要解决的问题更糟。**

品牌是可选的。把 `BRAND_HEADER` 设成一个正则，报告页眉必须匹配它；不设这条规则就不生效。

## 加一个包

```
skills/<包名>/
├── README.md          给人看的，不加载
├── <入口>.md          frontmatter 里写 entry: true
└── <成员>.md          由入口点名加载
```

frontmatter 必填 `name`、`version`、`description`。入口另需 `triggers`；**成员不能有** ——构建会拒绝没有恰好一个入口的包，成员按设计就是关键词打不到的。

`description` 是模型路由时唯一看得到的东西。**要写"什么样的请求该来这里"，不是写这个文件里有什么。**

`_` 开头的文件夹不参与构建，用于归档和未完成的东西。
