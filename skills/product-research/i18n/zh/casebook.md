# 实测案例库

**这份文件回答"为什么"，不回答"做什么"。**做什么在主方法，够不够在 `contract.json`。

## 读这份文件前必须知道的两件事

**一、案例是失败记录，不是清单。**"实测某产品有 25 个视觉模板"不是让你去找 25 个模板，是让你注意"模板构成能反推它认定的客户在做什么"。

**二、每条案例都有「不适用于」一栏，那一栏和判据一样重要。**

⚠️ **实测**：早期案例只写了"探测 `/customers` 返回 404"，没写前提和边界。跨模型测试时，模型在一份完全无关的报告里写下"没有客户案例页（`/customers` 返回 404）"——**而那次根本没探过这个路径。**

**残缺的案例比没有案例更危险**：它给出一个具体结论，却不给出这个结论成立的条件，于是被当成通用事实搬走。**所以每条案例必须写满七栏，缺栏的案例不许进这个文件。**

## 案例格式

| 栏 | 作用 |
|---|---|
| **前提** | 什么形态的产品、当时成立什么条件 ← **决定这条案例能不能用在手上这个产品上** |
| **做了什么** | 当时采取的动作 |
| **结果** | 实际发生了什么 |
| **机制** | 为什么会这样，可推广的原理 |
| **判据** | 这条案例产出的规则，不含具体产品的细节 |
| **不适用于** | 这条规则在什么情况下反而是错的 ← **防止过度泛化** |
| **怎么复现** | 拿到新产品时如何快速验证这条是否适用（有则写，无则写"不适用"） |

## 形态覆盖矩阵

⚠️ **看清楚哪些形态是实测过的，哪些是推断的。**在未实测的形态上，本方法的可靠性没有证据支撑。

| 产品形态 | 实测样本 | 覆盖到的环节 | 未覆盖 |
|---|---|---|---|
| **自助 SaaS**（有公开定价） | 4 个 | 取证、定价解剖、口碑、交付 | — |
| **企业销售制**（无公开定价） | 2 个 | 案例研究、结构化数据、分销结构 | 云市场合约价、招聘岗位反推 |
| **消费级应用**（有移动端） | 1 个 | 应用商店评论、版本节奏 | 榜单位置、买量信号 |
| **开发者工具 / API** | 2 个 | 端点结构、包下载量 | 限额与错误码的完整解剖 |
| **早期产品**（无口碑无案例） | 1 个 | 缺席即证据、获客设计反推 | 无 |
| **开源 / 开放核心** | 1 个 | 许可证判读与变更史、付费墙定位、仓库指标、自托管与云的边界 | 尚未测过**仍处于开放核心状态**的产品（本次样本已转全 MIT）；贡献者的雇员/外部比例未验证 |
| **平台 / 市场**（双边） | 1 个 | 命名空间归属、供给侧速率、抽成取证路径、需求侧的不可测边界 | 审核／入驻规则未取证；**需求侧本质不可测**（C-42），不是待补而是天然边界 |

**遇到未实测形态时的纪律**：照常执行方法，但在报告的边界一节写明"该形态本方法尚无实测校准"，**不要假装有把握**。

# 一、取证阶段

## C-01 先探测后拿索引，会得出完全相反的结论

| 栏 | 内容 |
|---|---|
| **前提** | 早期产品，入口只有一个登录页；多语言站；路径带 locale 前缀 |
| **做了什么** | 拿到域名后直接在裸域上探 20 个标准路径（`/pricing`、`/about`…） |
| **结果** | 19 个 404。据此判断"这是个单页产品，几乎没有内容" |
| **真相** | `sitemap.xml` 里有 **334 个 URL、20 个语言**。真实路径是 `/en/pricing`、`/zh/pricing`，裸路径当然全 404 |
| **机制** | 探测验证的是"我猜的路径存不存在"，索引给出的是"它实际有什么"。**猜错了路径，探测结果全是假阴性** |
| **判据** | **先拿路径空间（sitemap / llms.txt / robots.txt），再探测。**顺序反了会得出方向相反的结论 |
| **不适用于** | 无 sitemap 且 robots.txt 为空的站——此时只能靠探测，但要在报告里写明"路径空间未知，缺席结论不可靠" |
| **怎么复现** | `curl -sL <域名>/sitemap.xml \| grep -c '<loc>'`；数量与探测命中数差一个量级即说明踩了这个坑 |

## C-02 404 页面里挂着公司底盘

| 栏 | 内容 |
|---|---|
| **前提** | 企业销售制；站点用 WordPress + SEO 插件（Yoast / RankMath 一类） |
| **做了什么** | 探测 `/llms.txt`，返回 404，本来准备丢弃 |
| **结果** | 那个 404 页面的 HTML 里嵌着完整的 schema.org `Organization` 块：员工区间、成立年份、八个办公室城市、公关邮箱，外加一段含关键宣称的官方定位文案 |
| **机制** | SEO 插件把组织级 JSON-LD **注入每一个页面模板，包括 404 模板**。它是给搜索引擎读的，从来没人清理 |
| **判据** | **任何一次抓取（哪怕 404）都先在 HTML 里搜 `application/ld+json`，再决定丢不丢。**重点看 `numberOfEmployees`、`foundingDate`、`address`、`sameAs` |
| **不适用于** | 纯前端框架站（Next.js / SPA）的 404 常常只有一个空壳，没有 JSON-LD。**另外 `description` 是厂商自己写的，属宣称不属事实**，要进宣称清单 |
| **怎么复现** | `curl -sL <域名>/llms.txt \| grep -o 'application/ld+json' \| head -1` |

## C-03 robots.txt 的 Disallow 清单泄露真实商业动作

| 栏 | 内容 |
|---|---|
| **前提** | 自助 SaaS，官网有明码标价（45 到 329 美元分七档） |
| **做了什么** | 读 `robots.txt` 的 Disallow 列表 |
| **结果** | 列表里躺着六个促销落地页：终身买断、月付六折、季付减 150、**年付减 500**、**首月 77% off** |
| **机制** | Disallow 里放的是**它不希望被搜索引擎看到的东西**：促销页、按渠道定制的报价页、试用漏斗、已下线但可访问的旧产品。**这些恰恰是真实商业动作** |
| **判据** | **官网价不等于成交价。**把 Disallow 清单与官网价并排看，差额就是渠道折扣空间。对采购者的结论是"进门前先问折扣" |
| **不适用于** | **企业销售制产品的 robots.txt 通常很干净**——它的价格谈判发生在会议室，不在落地页。实测某企业级产品的 robots.txt 只有插件默认配置，无任何促销页，**这本身也是信息**（说明它不打自助渠道） |
| **怎么复现** | `curl -sL <域名>/robots.txt \| grep -i disallow` |

## C-04 静态抓取拿不到 = 页面上没有？错

| 栏 | 内容 |
|---|---|
| **前提** | 自助 SaaS；定价页返回 200、正文完整；价格由前端脚本按下拉框计算 |
| **做了什么** | 只做静态抓取，在 HTML 正文里找价格 |
| **结果** | 一个数字都没有。据此写下"**定价页不给任何金额，要登录后才能看到价格**"，并围绕它推出"定价不透明是它的设计"整段判断 |
| **真相** | 用浏览器打开，**七档价格明明白白挂在页面上**；逐档点下拉框，每档一个价 |
| **机制** | 把"我没抓到"当成了"它不给"。现代站点普遍用脚本渲染价格、额度、限额这类关键数字 |
| **判据** | **凡是"某页面上没有 X"的结论，必须渲染后确认。**交互控件（下拉框、档位切换、月付/年付开关、地区选择）**必须逐个操作**——只看默认值等于只看了七分之一 |
| **不适用于** | 服务端渲染的站点与纯文档站，静态抓取是可靠的，不必每页都开浏览器。**判据是：抓下来"什么都没有"时才必须渲染**，有内容时不必 |
| **怎么复现** | `curl -sL <定价页> \| grep -oE '\$[0-9]+'`，无结果则必须渲染复核 |

## C-05 登录墙不是墙：官方视频里全是真实界面

| 栏 | 内容 |
|---|---|
| **前提** | 产品完全在登录墙后，无公开文档站、无演示页 |
| **做了什么** | 写下"产品界面拿不到"，截图一栏留空。**连续五轮都这么写**，理由是"环境无渲染能力" |
| **结果** | 第六轮实际去试：浏览器工具能开页能截图，本机 Chrome 无头模式能把 PNG 写到磁盘。**从来就能截，是没试过。**再顺着官方频道抽帧，拿到了登录后的真实界面 |
| **机制** | 厂商自己的教学视频是**成本最低的真实 UI 来源**——它必须录屏才能教用户 |
| **判据** | 三步：`yt-dlp --flat-playlist --print "%(id)s \| %(title)s" <频道>/videos` 列标题 → 选片 → `ffmpeg -ss <秒> -i v.mp4 -frames:v 1 out.png` 抽帧。**标题即情报**：`How to connect…` 是主界面，`NEW in…` 是最新功能（常比官网新） |
| **不适用于** | **不是所有教学视频都有录屏。**实测某产品的 2 分钟上手视频全程是讲解人头 + 标题卡，零界面。**要先做缩略图矩阵**（`ffmpeg -vf "fps=1/8,tile=4x3"`）确认有录屏再下手，否则白下载 |
| **怎么复现** | 从 JSON-LD 的 `sameAs` 或页脚拿官方频道 URL，先列标题 |

## C-06 视频不一定在 YouTube

| 栏 | 内容 |
|---|---|
| **前提** | 企业级产品，功能页嵌了演示视频 |
| **做了什么** | 直接用 `yt-dlp` 抓页面上的视频 |
| **结果** | 嵌的是 **Vimeo**，带鉴权参数（`h=...`），player config 返回 403，`yt-dlp` 报 OAuth 401。**但同一家的 YouTube 频道是敞开的** |
| **机制** | 厂商常把"正式演示"放在带权限的 Vimeo，把"教学与营销"放在 YouTube |
| **判据** | **先从页面 HTML 里找嵌入源**（`grep -oE 'youtube\|vimeo\|wistia\|loom'`），按源选工具；一个源被拦不等于拿不到，换官方频道再试 |
| **不适用于** | 无公开视频渠道的产品（多为早期或纯企业销售制）。此时截图一项按 `absent` 豁免，但要写明查过哪几个渠道 |
| **怎么复现** | `curl -sL <功能页> \| grep -oE '(youtube\|vimeo\|wistia\|loom)[^"'"'"']*' \| sort -u` |

## C-07 索引列出来不等于读过

| 栏 | 内容 |
|---|---|
| **前提** | 开发者工具，有完整文档站与索引 |
| **做了什么** | 把文档索引打印出来，看到了 `/api/credits.md`、`ai-video-credits.md` 等页面，**没有点开** |
| **结果** | 报告里写"超额计费官网未说明""额度能生成多少内容官网没写"，并列成**待测表推给客户**。实际两条都写在它自己的文档里，而且那两个文件名就在我打印出来的索引里 |
| **机制** | 索引是地图不是内容。**列出来产生了"我已经知道了"的错觉** |
| **判据** | **索引中凡涉及定价、额度、限额、配额、错误码的页面，逐个点开读正文。**这是进入检索前的闸门 |
| **不适用于** | 无 |
| **怎么复现** | 交付前反查：报告里每一句"官网未说明"，回索引里搜对应关键词 |

## C-08 状态码要分三类，200 也不等于拿全了

| 栏 | 内容 |
|---|---|
| **前提** | 跨多个产品反复出现 |
| **做了什么** | 把非 200 一律当成"不存在" |
| **结果** | 三种误判：① `/pricing` 返回 **308**，跟随后是 `www.` 版本 200，被记成"无定价页"；② 某站 14 个路径**全部 403**（换 UA 仍 403），按"缺席即证据"会得出"这产品什么都没有"；③ 某定价页 **200 且正文完整**，但价格全靠脚本渲染，抓下来零个数字 |
| **机制** | 301/308 = 有；401/403/429 = 被拦；**只有 404 才是缺席**。而 200 只保证"有 HTML"，不保证"有内容" |
| **判据** | 四分类：**跟随重定向记最终 URL / 被拦要换通道再判 / 只有 404 进缺席推断 / 关键页 200 后仍需渲染复核** |
| **不适用于** | 无 |
| **怎么复现** | `curl -sL -o /dev/null -w "%{http_code} %{url_effective}\n" <url>` |

## C-09 先穷尽目标站，再向外检索

| 栏 | 内容 |
|---|---|
| **前提** | 该环境下抓页免费、对外检索按次计费 |
| **做了什么** | 拿到产品后先去搜索引擎查"XX competitors"、"XX pricing" |
| **结果** | 一轮调研只读了 2 个页面（其中一个还是聚合站），**却烧掉了全部检索额度**。而同轮实测另一产品的 11 个标准路径全部 200、全部免费可读 |
| **机制** | 目标站自己的页面是**密度最高、成本最低、可信度最高**的证据源 |
| **判据** | **先穷尽目标站，再向外找。**这个顺序与成本无关，与证据密度有关——换个计费模型它依然成立 |
| **不适用于** | 目标站被全站拦截时（见 C-08 情形②），只能反过来先做外部检索。此时要在报告里声明一手证据缺失 |
| **怎么复现** | 交付前统计：一手页面数 vs 检索次数。前者小于后者即为顺序错误 |

# 二、判断阶段

## C-10 缺席即证据，但"缺席"必须是确凿的 404

| 栏 | 内容 |
|---|---|
| **前提** | 开发者工具，小团队 |
| **做了什么** | 探测 `/pricing`、`/customers`、`/careers`、`/security`，四个全 404 |
| **结果** | 这四个"没有"合起来是一个明确结论：**小团队、没有企业销售动作、不打大客户** |
| **机制** | 一个公司会做哪些页面，反映它在服务谁。**缺席是有信息量的，前提是确实缺席** |
| **判据** | 把 404 的路径按语义分组：**无定价页 → 企业销售或未定价；无 security/合规页 → 不打受监管行业；无 status 页 → 无可用性承诺；无 careers → 不在扩张** |
| **不适用于** | ⚠️ **路径别名会造出假缺席**：实测 `/terms` 为 404，据此写"法务尚未规范化"，而 `/terms-of-service` 与 `/privacy-policy` 都是 200。**判缺席前先试常见别名**（`-of-service`、`-policy`、`legal/` 前缀、locale 前缀） |
| **怎么复现** | 每个判为缺席的路径，至少再试两个别名 |

## C-11 从"没有团队页"推不出"实质单人"

| 栏 | 内容 |
|---|---|
| **前提** | 自助 SaaS，无团队页、无招聘页 |
| **做了什么** | 直接写"**实质单人**"，并把整节"单人依赖是最大风险"建在这个前提上 |
| **结果** | 推得太满。补做三条独立旁证后才站得住：npm 包发布者是创始人本人、GitHub 组织公开成员为 0、仓库全部提交作者为同一人 |
| **机制** | **未发现 ≠ 不存在。**单一信号只能支撑"公开信息显示…"，不能支撑事实断言 |
| **判据** | 结论分四级：**观察事实 / 高置信推断（≥3 条独立信号）/ 中置信 / 低置信**。写成"公开信息显示团队极小（无团队页、无招聘页），未见第二人公开署名" |
| **不适用于** | ⚠️ **三角验证通道依赖产品形态**：实测某消费级 SaaS，npm 无官方包、GitHub 无可定位组织，**这套通道整体失效**。改用应用商店评论数、招聘平台、媒体报道 |
| **怎么复现** | 报告里每个"实质/事实上/显然"，回查支撑它的独立信号有几条 |

## C-12 长尾排名的短期变化是噪声，不是信号

| 栏 | 内容 |
|---|---|
| **前提** | Tranco 域名排名；被比较的玩家分布在 3,000 位到 100 万位之间 |
| **做了什么** | 写下"分发层在缩、生成层在退、一体化层在涨"这套三层结论 |
| **结果** | 换一天用新数据复核，**三句里只有一句站得住**。"一体化层在涨"的四个证据**全部落在 22 万位以后**——而本方法自己就规定长尾变化属噪声 |
| **机制** | **用自己禁止的证据支撑了一个漂亮的结论。**叙事越整齐，越可能是挑出来的 |
| **判据** | 可信区间约 5 万位以内；**每一层至少要有一个可信区间内的锚**，全靠长尾撑起来的层只能写"证据不足"。**同一把尺子量所有层。**判据：删掉长尾玩家后结论还成不成立 |
| **不适用于** | 头部（千位量级）的变化有解释力，可以用；15% 级别的变动即使在 2 万位也站得住 |
| **怎么复现** | 把结论依赖的每个玩家排名列出来，划掉 5 万位以后的，看结论还剩什么 |

## C-13 Tranco 测的是知名度，不是访问量

| 栏 | 内容 |
|---|---|
| **前提** | 任何有网站的产品 |
| **做了什么** | 两次误用：① 断言"对纯 API 产品会系统性低估"；② 把长尾 30 天波动当趋势 |
| **结果** | 两条都被推翻。① Tranco 五个来源里**三个是 DNS 类**（Cloudflare Radar、Farsight 被动 DNS、Cisco Umbrella），**包含非浏览器流量**，API 子域的请求按注册域名聚合会算进主域，**低估方向不成立**；② 见 C-12 |
| **机制** | 五源 Dowdall 平均：CrUX 真实页面访问 + 三种 DNS + Majestic 反向链接。**测的是显著性，换算不出访问量** |
| **判据** | **只用量级与相对位置，不换算访问量。**必须写口径说明与失真方向 |
| **不适用于** | ⚠️ **企业销售制产品另有一层偏差**：客户经销售接触、日常使用在 `app.` 子域内，官网流量系统性低估其真实规模。**但这层偏差对同赛道所有玩家一致，所以相对位置仍可读** |
| **怎么复现** | `curl -s https://tranco-list.eu/api/ranks/domain/<域名>` |

## C-14 证据标准必须对称

| 栏 | 内容 |
|---|---|
| **前提** | 竞品对比表，目标产品与竞品并列 |
| **做了什么** | 对目标产品的每个数字都要求逐字引文并标注置信度，**而竞品行里的融资额、ARR、员工数直接采用第三方估算站的数字当事实** |
| **结果** | 同一份报告里两套标准。外部评审直接指出 |
| **机制** | 对熟悉的对象要求严，对陌生的对象要求松——**这是最容易发生且最难自查的偏差** |
| **判据** | **竞品行的每个数字与目标行同标准**：标来源、标是否估算、标日期。做不到就写"未核实" |
| **不适用于** | 无 |
| **怎么复现** | 随机抽竞品表里 3 个数字，逐个问"原话是什么、URL 是什么" |

## C-15 阶梯定价是分段函数，不许采样几点就报区间

| 栏 | 内容 |
|---|---|
| **前提** | 两个产品按账号数阶梯计价，价格随数量分段变化 |
| **做了什么** | 取 6 个采样点比价，报出"30 到 200 之间 A 更便宜" |
| **结果** | 实际有**四个交叉区间**（1–6、7–20、21–26、27–40、41–280、281 持平、282+）。外部评审找出了 41–280 这一段，我自己又发现漏了 21–26 |
| **机制** | 分段函数上采样几个点，必然错过交叉点 |
| **判据** | **逐点求解或写出分段表达式**，不许用采样点外推 |
| **不适用于** | 单一线性计价（每单位固定价）时采样是安全的 |
| **怎么复现** | 把两条价格曲线写成函数，解交点 |

## C-16 比价前先确认交付的是同一件事

| 栏 | 内容 |
|---|---|
| **前提** | 五个同品类产品 |
| **做了什么** | 直接把月付价放进一张表比较 |
| **结果** | 五家计价单位互不相同：按频道每个计费、按频道打包、按工作区 + AI 点数、按坐席、按用量。**同一张表里的数字不可比** |
| **机制** | 计价单位就是商业模式本身，也直接说明它为谁设计 |
| **判据** | **先归一化到同一计价单位再比**；并先确认两边交付的是同一件事（有的产品含生成，有的只做分发） |
| **不适用于** | 无 |
| **怎么复现** | 比价表里每一列写明"每什么收费" |

## C-17 评价平台测的不是同一件事

| 栏 | 内容 |
|---|---|
| **前提** | 同一产品在多个评分站有收录 |
| **做了什么** | 看到 G2 4.6 分与 Trustpilot 低分区互相矛盾，试图调和成一个"综合评价" |
| **结果** | 两次撞到同一模式：G2 4.6（188 条）vs Capterra 双峰分布；SourceForge 4.7 vs Trustpilot 2.0 |
| **机制** | **G2 / SourceForge / TrustRadius** 大量评论来自厂商邀请，样本偏满意用户，测的是**功能满意度**；**Trustpilot / Capterra 低分区**以自发投诉为主，测的是**商业体验**（账单、取消、退款、客服） |
| **判据** | **两类都查，不许调和。**分数差异本身是发现：**功能高分 + 商业体验低分 = 产品能用但商业动作激进** |
| **不适用于** | 评论总数少于 50 的评分不能当口碑结论，但单条具体抱怨仍可作线索引用（标明是单条） |
| **怎么复现** | 至少各取一个"邀请型"和一个"自发型"平台 |

## C-18 评论要按时间分组，不只按正负分

| 栏 | 内容 |
|---|---|
| **前提** | 产品有多年评论积累 |
| **做了什么** | 按正面/负面两栏整理引文 |
| **结果** | 按年份重排后浮现出完全不同的图景：5 星集中在 2019–2023（"三倍 ROAS""等于印钞机"），1 星集中在 2023–2025（账单、难取消、不退款）。**按正负分栏会完全掩盖这个规律** |
| **机制** | 时间分布反映的是商业策略的变化，不是随机波动 |
| **判据** | **把引文按年份排一遍。**负面集中在近期而正面集中在早期 → 产品或商业动作发生了变化 |
| **不适用于** | ⚠️ **应用商店评论的时间线可能被版本号取代**：实测某产品最近 100 条评论只标版本号不标日期，**要按版本号排序并换算大致时间**，否则这条判据用不上 |
| **怎么复现** | 引文清单加一列年份，按年份排序 |

## C-19 历史总分掩盖近期塌陷

| 栏 | 内容 |
|---|---|
| **前提** | 消费级应用，应用商店有三万条以上历史评论 |
| **做了什么** | 采用商店显示的总评分 4.73 |
| **结果** | **最近 100 条的均分只有 3.17**，其中 34 条一星。总分是十几年积累撑住的 |
| **机制** | 大样本历史均分对近期变化极不敏感。**总分与近期分的差距会随时间自然收敛——意味着不解决就会持续下滑** |
| **判据** | **历史总分与近期样本分开报。**两者差距大本身就是结论 |
| **不适用于** | 评论总数少（<200）时两者差异多为噪声 |
| **怎么复现** | `curl -s "https://itunes.apple.com/lookup?id=<appid>"` 取总分；RSS 取最近评论算均分 |

## C-20 先分层，再比较

| 栏 | 内容 |
|---|---|
| **前提** | 赛道里的玩家干的不是同一段活 |
| **做了什么** | 某轮把赛道拆成三层（把内容发出去 / 把内容做出来 / 两者一体），据此判断价值往哪迁移——**那是该报告最有价值的一节** |
| **结果** | **但方法里没有这一步。**下一轮换个产品，整块分析直接消失，只剩功能层面的空位罗列 |
| **机制** | **做过一次但没写进流程的分析，不会再发生。**这与 C-24 是同一个病 |
| **判据** | 凑齐玩家之后、比较之前，先问"这些玩家干的是同一件事吗"。**按输入→输出切段**：已有内容→已发布 = 分发层；素材→成品 = 生成层；两段都吃 = 一体化层 |
| **不适用于** | 单层赛道（所有玩家干同一段）时不必强行分层，但要说明"已确认为单层" |
| **怎么复现** | 每个玩家写一行"输入什么 → 产出什么"，看能不能归成两类以上 |

# 三、交付阶段

## C-21 图必须嵌入，不能给路径

| 栏 | 内容 |
|---|---|
| **前提** | 文档站里有 19 张真实界面截图 |
| **做了什么** | 报告里列出这些图的文件路径当证据 |
| **结果** | 那些路径**实际是 404**——文档站的内部相对路径，外部取不到。**列一串死链当证据，比不写更糟** |
| **机制** | 未验证的引用会被当成已验证 |
| **判据** | **能嵌就嵌（先验证 URL 返回图片类型）；取不到就写明"无图"，不要给链接假装有图** |
| **不适用于** | 无 |
| **怎么复现** | 报告里每个图片链接跑一次 `curl -I`，确认 `content-type: image/*` |

## C-22 内联 HTML 会毁掉第一屏

| 栏 | 内容 |
|---|---|
| **前提** | 报告需要在多种渲染器里传播（预览器、PDF 导出、他人编辑器） |
| **做了什么** | 页眉写成 `# <img src="data:image/png;base64,..." width="30"> 标题`，为的是控制 logo 尺寸 |
| **结果** | 用户的预览器不渲染内联 HTML，**4,600 字符的 base64 被当成正文，以 H1 字号糊满整个第一屏** |
| **机制** | 内联 HTML 在很多渲染器里被原样输出。**base64 一旦被原样输出，不是"样式差一点"，是第一屏被毁掉** |
| **判据** | **只用纯 markdown。**图片一律 `![](src)`，尺寸靠选对分辨率的源文件解决（页眉用 32px PNG），不靠 `width` 属性。`<sub>` `<br>` `<div>` `<span>` 同禁 |
| **不适用于** | 目标渲染器确定且支持 HTML 时（如自建站点）可放宽，但交付给外部一律从严 |
| **怎么复现** | `grep -E '<(br\|div\|span\|img\|sub)' <报告>` |

## C-23 报告是交付物，不是工作日志

| 栏 | 内容 |
|---|---|
| **前提** | 报告经过多轮修订 |
| **做了什么** | 正文里留下"本报告已修订""初版我写错了""上一轮我完全漏掉""这轮调研过的所有产品里最多""纪律说明：我没有去抓取 Disallow 页面" |
| **结果** | 客户买的是结论，不是作者怎么得出结论的。**读者要绕过作者的认知过程才能读到内容** |
| **机制** | 修订痕迹、内部术语、跨报告自比，都是只有作者关心的东西 |
| **判据** | 全部删掉。"边界"一节的写法是**"未取得什么 → 对判断有什么影响"**，不是"我没做什么"。前者是专业，后者是免责 |
| **不适用于** | 无 |
| **怎么复现** | `node scripts/check-report.mjs` 的 worklog / internal-jargon / method-leak 三条 |

## C-24 skill 存在但流程里没有它，等于不存在

| 栏 | 内容 |
|---|---|
| **前提** | `last_30_days` 这份方法一直在 skill 集里 |
| **做了什么** | 依赖关键词路由让模型自己想起来用它 |
| **结果** | **连续三轮一次都没用上。**同样的病后来又犯了两次：截图漏两轮、分层做过一次就消失 |
| **机制** | **方法没进执行顺序 = 方法不存在。**靠"记得去用"的规则一定会漏 |
| **判据** | 每个子方法必须在执行顺序里有明确的一步点名加载它；**且完成标准必须由代码检查，不能写在文档末尾靠人自觉** |
| **不适用于** | 无 |
| **怎么复现** | 拿子方法清单逐个搜执行顺序，搜不到就是孤儿 |

## C-25 不许给自己设不存在的限制

| 栏 | 内容 |
|---|---|
| **前提** | 用户从未要求报告要短 |
| **做了什么** | 连续三轮把内容往回收，还在方法里写了篇幅上限；某轮在输出上限还剩三分之二时用"因篇幅限制"跳过了六个模块 |
| **结果** | 用户原话："我没有给你设这个限制，你不要给自己设限" |
| **机制** | 把执行环境的约束误当成交付要求 |
| **判据** | **篇幅不是约束。**内容多就分批写、分批交付。禁止"因篇幅限制""后续同理"这类跳过 |
| **不适用于** | 部署环境确有硬上限时，用环境变量设闸门，**不要写进方法文档** |
| **怎么复现** | 搜报告里的"限于篇幅""后续同理""不再赘述" |

## C-26 相邻两列符号方向相反，用户一定读反

| 栏 | 内容 |
|---|---|
| **前提** | 排名表：排名数字越小越好，变化列正数越大越好 |
| **做了什么** | 两列并排，变化列写"+159,430" |
| **结果** | 用户把"前进 16 万位"读成了"后退 16 万位" |
| **机制** | 同一张表里两种相反的符号约定，读者不会逐列确认方向 |
| **判据** | **写前后两个值 + 文字方向**（"30 天前 735,952 → 现在 576,522，前进 159,430 位"），不写带符号的差值 |
| **不适用于** | 无 |
| **怎么复现** | 表里每个数字列问一句"变大是好还是坏"，答案不一致就要改写 |

## C-27 不许把活推回给客户

| 栏 | 内容 |
|---|---|
| **前提** | 需要试用级证据（额度能做多少、实际体验如何） |
| **做了什么** | 交付里放"待测"表格，列出让客户自己去验证的项 |
| **结果** | 用户原话："**用户找你就是为了不用自己去试**"。而且那一轮的两条"待测"，答案就在厂商自己的文档里（见 C-07） |
| **机制** | "待测"是把未完成的工作包装成交付物 |
| **判据** | 三条路依次试：**厂商自己的文档 → 第三方实测（评测视频、深度长帖）→ 能免费注册的就注册**。三条都不通时**给判据不给空表**（"如果你的用量是 X，按 Y 计算成本约 Z"） |
| **不适用于** | 无 |
| **怎么复现** | `grep -E '待测\|建议自行试用\|请自行验证' <报告>` |

# 四、跨模型执行

## C-31 模型会编造一个看起来合理的 URL

| 栏 | 内容 |
|---|---|
| **前提** | 需要引用一手页面作证据；标准路径命名规律性强（`/pricing`、`/docs`…） |
| **做了什么** | 模型自己拼出了一个符合命名习惯的 URL 并写进报告当证据 |
| **结果** | 该路径实为 404，从未被打开过。同一轮里还连续三次引用了同一个不存在的页面 |
| **机制** | 标准路径的命名太有规律，**"合理"与"存在"在模型这里几乎无法区分** |
| **判据** | **报告里出现的每个 URL，必须在本轮真实打开过或出现在检索结果里。**执行层可用"已见 URL 白名单"硬拦 |
| **不适用于** | ⚠️ 白名单一旦设得太死会拦掉合法的标准路径探测——实测出现过。**正确做法是先播种标准路径清单，再对清单外的 URL 拦截** |
| **怎么复现** | 抽报告里 3 个 URL 跑 `curl -I`，确认非 404 |

## C-28 举例会被当成本次的发现搬走

| 栏 | 内容 |
|---|---|
| **前提** | 方法文档里有具体的实测举例；换一个模型执行同一份方法 |
| **做了什么** | 文档里写着"实测 scrapecreators.com 的 `/customers` 全部 404" |
| **结果** | 模型在一份**完全无关**的报告里写下"没有客户案例页（`/customers` 返回 404）"——**那次的证据里根本没探过这个路径**。3 轮里 2 轮复现 |
| **机制** | **举例天然会污染输出。**写得越具体、越像发现，越容易被整段搬走 |
| **判据** | ① 每条案例必须写满七栏，**特别是"前提"和"不适用于"**；② 报告里每个状态码、路径、数字、公司名必须能指回本次证据；③ 交付前用检查器把方法文档出现过的产品名标出来逐条确认 |
| **不适用于** | ⚠️ **不要简化成"这些名字一律不许出现"。**实测把这条设成硬拦截后，一份报告里三个名字全被拦下，**而它们都是当天现拉的数据**。硬禁令会逼着作者删真实证据，比串味更糟。**判据是证据，不是名字** |
| **怎么复现** | 拿方法文档里的产品名做黑名单跑一遍，逐条问"这个数据是本轮取的吗" |

## C-29 模型会把规则原文抄进交付物

| 栏 | 内容 |
|---|---|
| **前提** | 方法文档用散文写规则；换模型执行 |
| **做了什么** | 文档里写"边界一节要写未取得什么对判断有什么影响，**而不是简单列出'没做哪些事'**" |
| **结果** | 模型把这句指令改写成了报告正文："本节说明本轮证据搜集的限制，以及这些未达成的部分会如何影响后续判断，**而不是简单列出'没做哪些事'**"。3 轮里 3 轮出现（含"高置信""本轮未""缺席即证据"等内部术语） |
| **机制** | 散文写的指令和散文写的内容，**模型分不清哪句是给它看的、哪句是给客户看的** |
| **判据** | 交付前用检查器扫内部术语与规则措辞；**长期解法是把"要求"从散文移到机器可读的契约**，指令与内容物理分离 |
| **不适用于** | 无 |
| **怎么复现** | `grep -E '高置信\|缺席即证据\|本轮未\|而不是简单列出' <报告>` |

## C-30 不同模型的失败方式不同，兜底策略也要不同

| 栏 | 内容 |
|---|---|
| **前提** | 同一份方法 + 同一份证据，在两个模型上各跑 3 轮 |
| **做了什么** | 比较两者输出 |
| **结果** | **快模型**：结论与结构全对（定价解剖、隐藏折扣、附加费、宣称冲突全抓到），**问题全在格式**——3 轮里 2 轮用了 `<br>`、2 轮带对话式开场白、1 轮把方法版本号写进页眉。**慢模型**：行文更好、判断更细，**但 3 轮里 2 轮编造证据**（把方法文档的举例写成本次发现），3 轮里 3 轮泄露内部术语 |
| **机制** | 格式问题是机械的，代码能兜住；**编造证据是实质的，代码兜不住** |
| **判据** | **快模型 + 强制检查器**是更好的组合；慢模型只在需要更细的商业判断时用，且用完必查。**不能裸跑任何一个** |
| **不适用于** | 只测过两个模型、一个用例。**换模型族（非同厂）时这个结论没有证据支撑，要重测** |
| **怎么复现** | 固定一份证据 + 固定提示，每个模型跑 3 轮，用检查器统计失败类型分布 |

# 六、开源 / 开放核心

## C-32 付费墙可能就是仓库里的一个目录

| 栏 | 内容 |
|---|---|
| **前提** | 开放核心产品（开源主体 + 闭源商业模块）；有公开仓库 |
| **做了什么** | 读仓库根目录的 `LICENSE` 全文，而不只看 GitHub 页面上显示的许可证名 |
| **结果** | LICENSE 开头就写明了付费墙的**精确坐标**："All content that resides under `packages/features/ee` and `apps/api/v2/src/ee` (Commercial License) is licensed under `ee/LICENSE`；其余走 AGPLv3"。而 `ee/LICENSE` 里写着须持有企业版订阅、**按 host 数计费**、"禁止复制、合并、发布、分发、转授权或销售" |
| **机制** | 开放核心产品必须在法律文本里划清哪部分收费，**所以 LICENSE 是唯一一份不会含糊的付费墙说明书**。营销页会说"企业版功能更多"，LICENSE 会说"具体是这两个目录" |
| **判据** | **开源产品的定价解剖从 `LICENSE` 全文开始，不是从定价页开始。**顺序：LICENSE 全文 → 找出被划为商业授权的目录 → 进那个目录看有哪些模块 → 才是定价页。**目录名就是付费功能清单** |
| **不适用于** | 单一许可证的纯开源项目（LICENSE 里没有目录例外条款），此时付费墙不在代码里，要去看托管、支持、认证这些代码外的收费项。**GitHub 页面只显示一个许可证名，看不出有没有例外条款——必须读全文** |
| **怎么复现** | `curl -sL https://raw.githubusercontent.com/<org>/<repo>/main/LICENSE \| head -20`，搜 `Portions`、`directory`、`Commercial` 三个词 |

## C-33 GitHub API 返回 301，意味着改过名或换过组织

| 栏 | 内容 |
|---|---|
| **前提** | 用已知的 `org/repo` 去调 GitHub API |
| **做了什么** | `curl https://api.github.com/repos/<org>/<repo>` |
| **结果** | 返回 **301 Moved Permanently** 与一个 `repositories/<id>` 地址。跟过去发现仓库已改名，**主页域名也换了** |
| **机制** | GitHub 对改名/转移的仓库保留永久重定向。**301 是改名的第一个信号，而改名往往伴随定位或商业模式的变化** |
| **判据** | **不要用 `-L` 静默跟随了事。**看到 301 就去查：改成了什么名、什么时候改的、主页换了没有。**改名本身要写进报告的"近期变化"一节** |
| **不适用于** | 组织内部的普通重命名（如 `foo` → `foo-js`）可能只是整理，不必上纲上线。**判据是主页域名或许可证有没有同时变**——只改名不改别的，多半只是整理 |
| **怎么复现** | `curl -s https://api.github.com/repos/<org>/<repo> \| grep -E '"message"\|"url"'` |

## C-34 许可证变更会夹在普通提交里，只能从 git 历史看出来

| 栏 | 内容 |
|---|---|
| **前提** | 开放核心产品，需要判断它的商业模式是否变过 |
| **做了什么** | 查 `LICENSE` 文件的提交历史，而不是只看当前内容 |
| **结果** | 当前是 **MIT，21 行，无任何限制**。但历史显示：**2026-04-15** 的一次提交把 670 行的 AGPLv3 + 商业条款换成了 MIT，**同时删掉了整个 `ee/LICENSE`**。而那次提交的标题是 **`refactor: Cal.diy (#28903)`，改了 300 个文件，标题里一个字都没提许可证** |
| **机制** | 许可证变更是重大商业动作，但**它在 git 里只是一次文件修改**，很容易被裹进大型重构。**没有公告不等于没发生** |
| **判据** | **查 `LICENSE` 的提交历史，不要只看当前内容。**每一次变更都要看 diff——方向是收紧（开源→BSL/商业）还是放开（商业→MIT）**，这是判断商业模式走向最硬的证据** |
| **不适用于** | 从未变更过许可证的项目（历史只有一次初始提交）——此时这条不产出信息，但**"从未变更"本身可以写进报告**作为稳定性证据 |
| **怎么复现** | `curl -sL "https://api.github.com/repos/<org>/<repo>/commits?path=LICENSE&per_page=10"`，再对可疑 sha 取 diff |

## C-35 付费墙从"目录边界"搬到"托管边界"

| 栏 | 内容 |
|---|---|
| **前提** | 同一家公司，代码全部 MIT 开放，但仍在正常收费 |
| **做了什么** | 分别打开商业域名与仓库主页域名 |
| **结果** | 两个域名是**两个东西**：商业域名是云产品（定价页、企业版、登录），仓库主页域名是**自托管文档站**（安装、数据库迁移、Docker、八家云平台的部署指南）。定价：个人永久免费，团队 **$12/人/月**，另有 **$28** 档 |
| **机制** | 代码全开之后，付费墙不可能再画在代码里，**只能画在"谁来运维"上**。给自托管配一个独立域名和完整文档，是把"你自己扛"变成一个有名字的、体面的选项——**同时也把云版的价值定义成"我们替你扛"** |
| **判据** | 开源产品的商业模式看两件事：**① 代码里还有没有闭源部分（读 LICENSE）；② 没有的话，收费理由是什么**（托管 / 支持 / 认证 / 合规 / 托管数据）。**自托管文档的完备程度反过来说明它对云收入的信心**——文档越全，说明越不怕你自己装 |
| **不适用于** | 仍有闭源目录的开放核心产品，付费墙还在代码里（见 C-32）。**先判断属于哪一类，再选分析路径** |
| **怎么复现** | 查仓库的 `homepage` 字段与官网主域是否一致；不一致就分别打开看 |

## C-36 仓库指标里混着机器人，提交集中度比总数有用

| 栏 | 内容 |
|---|---|
| **前提** | 开源项目，需要判断"社区活跃"是真是假 |
| **做了什么** | 拉贡献者列表（约 400–500 人），看提交分布而不只看总数 |
| **结果** | **前 10 人占 56% 的提交**，其中**第 5 名是翻译机器人**（764 次提交）。star 47,095、fork 14,624 |
| **机制** | star 和 fork 测的是关注度，不是参与度。**贡献者总数会把一次性提交（改错别字、翻译）和核心开发者算成同一个人头**，而机器人会被算进"人" |
| **判据** | **剔除 bot（登录名含 `bot`、`[bot]`、`crowdin`、`dependabot`、`renovate`）后**，看前 10 人的提交占比：**高度集中 = 公司项目开源发布；分散 = 真社区**。两者的可持续性完全不同 |
| **不适用于** | 单人或极小团队项目——集中度必然是 100%，这条不产出信息。**样本太小时改看提交时间跨度与最近一次提交距今多久** |
| **怎么复现** | `curl -sL "https://api.github.com/repos/<org>/<repo>/contributors?per_page=100"`，看 `Link` 头的 `rel="last"` 估总页数 |

## C-37 开源产品的 robots.txt 干净，原因和企业销售制不同

| 栏 | 内容 |
|---|---|
| **前提** | 开源产品，有公开定价、可自助注册 |
| **做了什么** | 按 C-03 去读 `robots.txt`，预期能挖到促销落地页 |
| **结果** | 只有四条：`/sandbox`、`/api`、`/settings`、`/settings/my-account`，**全是应用内部路径，零促销页** |
| **机制** | C-03 成立的前提是"增长靠投放落地页"。**开源产品的增长靠仓库、文档和集成生态**，不靠折扣页，所以没什么要藏 |
| **判据** | **robots.txt 干净有两种完全不同的含义**：企业销售制 = 价格谈判在会议室；开源 = 增长渠道不在落地页。**要结合形态判读，不能一律解释成"没有隐藏折扣"** |
| **不适用于** | 有开源版但重度投放的商业公司（部分开放核心产品仍跑大量付费投放），此时 C-03 依然适用。**判据是看它有没有 `/offer/`、`/lp/`、`/promo/` 这类路径段** |
| **怎么复现** | `curl -sL <域名>/robots.txt`；Disallow 全是应用内路径 = 无投放漏斗 |

# 七、平台 / 双边市场

## C-38 平台的顶级路径属于卖家，200 不等于"平台方有这个页面"

| 栏 | 内容 |
|---|---|
| **前提** | 双边市场；卖家在平台上有自己的店铺，店铺地址直接挂在主域下（`平台域名/<店铺名>`） |
| **做了什么** | 按标准流程探测 `/pricing`、`/security`、`/about`… |
| **结果** | `/pricing` 返回 **200**，标题是 `PRICING`——**但那是一个卖家的店铺**，由某个用户创建，页面上有 3 条评分和"客户评价"模块。`/security` 也是 200，标题是 **"Oracle's store"**。而 `/terms`、`/enterprise`、`/careers`、`/docs` 确实是平台自己的页 |
| **机制** | 平台把顶级命名空间让给了卖家：**公司保留一小批 slug，其余全部落到店铺**。两者都返回 200，**状态码分不出来** |
| **判据** | 平台形态下，**每一个 200 的页面都要看 `<title>` 与页面结构确认归属**：出现店铺名、评分、"由 X 提供支持"这类元素的，是卖家页不是公司页。**不能按状态码判"平台有没有安全页"** |
| **不适用于** | 卖家页在子路径下（`/store/<名>`、`/u/<名>`）或子域下的平台——命名空间不冲突，标准探测照常可用。**先看一两个已知店铺的 URL 形状，再决定要不要逐页确认归属** |
| **怎么复现** | `curl -sL <域名>/pricing \| grep -oE '<title>[^<]*'`；标题里带 `store`、`'s`、或与公司名无关的词即为卖家页 |

## C-39 供给侧规模不在 sitemap 里，但"最新上架"feed 能算出上架速率

| 栏 | 内容 |
|---|---|
| **前提** | 双边市场，卖家列表是动态的、量大 |
| **做了什么** | 读 sitemap 想数供给侧规模 |
| **结果** | 主 sitemap **只有 35 条 URL**（全是公司页），类目 sitemap 有 **897 个类目页、12 个一级类目**，**但一个卖家列表都没有**。而 `robots.txt` 里还声明了第四个来源：一个 **"最新上架" RSS**。拉下来 100 条，全部带时间戳，跨度 **316 分钟** → **约 19 个/小时、455 个/天** |
| **机制** | 平台不会把动态生成的卖家页放进 sitemap（量太大、变化太快），**但"最新上架"是个营销/发现功能，它必须公开**。而它带时间戳，**100 条的时间跨度就是一次采样** |
| **判据** | 平台形态下，**sitemap 给结构，RSS/最新上架给速率**。用 `条数 ÷ 时间跨度` 算供给侧的上架速率——**这是少数能从外部拿到的硬指标**。类目树的深度与广度另测品类结构 |
| **不适用于** | 无公开 feed 的平台（多为封闭式或审核制市场）。**另外这个速率是"新增"不是"存量"**，不能反推总量；也不能排除刷量与测试数据 |
| **怎么复现** | `curl -sL <域名>/robots.txt \| grep -i sitemap`（feed 常混在 Sitemap 声明里），再取 `<pubDate>` 算跨度 |

## C-40 抽成写在 API 文档里，而且是拆散的

| 栏 | 内容 |
|---|---|
| **前提** | 双边市场，向卖家收取交易抽成 |
| **做了什么** | 找定价页想看抽成比例 |
| **结果** | 定价页是卖家店铺（见 C-38）。真正的费率线索在**开发者文档**里：一个 `List fees` 接口，返回"platform fees and processing fees"；文档索引里散着三个数字——**iOS 内购 2.7% + $0.30**（并直接对标"Apple 的 15–30%"）、**推荐商家返佣 30%**、**Whop 卡返现 5%**。**没有任何一个页面写着"平台抽成是多少"** |
| **机制** | 抽成必须对开发者可查询（要对账），**所以它一定在 API 里**；但对外它被拆成场景化的数字，并用"比对手便宜"的方式呈现 |
| **判据** | 平台形态下，**费率的取证顺序是：API 文档 → 帮助中心 → 卖家协议，最后才是定价页**。搜 `fee`、`payout`、`commission`、`take rate` 四个词。⚠️ **拿到单个百分比不要当成总抽成**——先确认它适用于哪个场景（支付方式、地区、业务类型） |
| **不适用于** | 无开发者 API 的平台（多为纯消费市场），此时改查卖家帮助中心与入驻协议 |
| **怎么复现** | `curl -sL <docs域名>/llms.txt \| grep -inE 'fee\|payout\|commission'` |

## C-41 llms.txt 有三种物种，读之前先判是哪一种

| 栏 | 内容 |
|---|---|
| **前提** | 目标站有 `/llms.txt` |
| **做了什么** | 跨三个产品分别读它们的 `llms.txt` |
| **结果** | 三种完全不同的东西：**① 营销文案**——通篇"leading""pioneered"，是写给 AI 读的宣传稿；**② 文档索引**——中立的页面清单，14KB；**③ 给代理的路由契约**——写明"开发者问题以 docs 的 llms.txt 与 MCP 服务器为准，**营销页只作定位参考，不要从中推断 API 行为**"，并列出两个 MCP 端点及其权限边界（其中一个"可以创建、修改、删除真实数据"） |
| **机制** | `llms.txt` 没有强制规范，**厂商想写什么写什么**。它写成什么样，本身反映它对 AI 渠道的认知程度 |
| **判据** | **读之前先判物种**：① 营销型 → 内容进宣称清单，不进事实；② 索引型 → 当路径空间用；③ 路由契约型 → **按它的路由走**，并且**它本身是一条产品情报**（说明该产品把 AI 代理当正式用户，通常还有 MCP） |
| **不适用于** | 无 `llms.txt` 的站点——退回 `sitemap.xml`。**⚠️ 但 404 页面仍要看 JSON-LD（C-02）** |
| **怎么复现** | `curl -sL <域名>/llms.txt \| head -40`，看开头三段是自夸、清单、还是规则 |

## C-42 双边市场的需求侧几乎测不到，要明说

| 栏 | 内容 |
|---|---|
| **前提** | 双边市场；供给侧可枚举，需求侧（买家）不可枚举 |
| **做了什么** | 供给侧拿到了硬数（455 个新商品/天、897 个类目）；需求侧尝试用站点知名度排名做代理 |
| **结果** | 只能拿到整站排名（该产品 17,988，同类：Patreon 541、Gumroad 2,896、Skool 5,577、Teachable 5,048、Kajabi 11,405）。**但整站流量既包含买家也包含卖家，还包含卖家发给自己客户的店铺链接带来的访问**——**这个数字无法拆分成需求侧规模** |
| **机制** | 买家不留公开痕迹。平台也不会公布 GMV 或买家数，除非上市或融资时披露 |
| **判据** | **双边市场的报告必须显式声明需求侧未测**，不要用整站流量冒充买家规模。能做的是：**用同类平台的排名做相对位置**，并说明这个代理同时混入了两侧流量。**⚠️ 单边数据不能推出平台健康度**——供给侧涨而需求侧不明时，正确表述是"供给侧在快速扩张，需求侧无法验证" |
| **不适用于** | 有公开 GMV／买家数披露的平台（上市公司、或主动公布指标的公司），此时直接用披露值 |
| **怎么复现** | 报告里搜"用户数""规模"，逐个问：这个数字是买家、卖家，还是两者混在一起 |

# 八、还没有案例的地方

**下面这些是本方法目前的盲区。遇到时照常执行，但要在报告边界一节声明"该情形本方法尚无实测校准"。**

| 盲区 | 为什么重要 | 需要什么样的案例来补 |
|---|---|---|
| **目标站全站被拦** | 一手证据整体缺失时的替代路径 | 一次实测：四级降级全部走完后还能拿到什么 |
| **非英语／非中文市场的产品** | 口碑源与检索通道完全不同 | 一次实测：日语、西语市场的评价平台与检索习惯 |
| **同一产品的纵向复查** | 方法的稳定性无从验证 | 隔 3 个月对同一产品重跑，比较结论差异 |
