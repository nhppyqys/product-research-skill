# 产品调研主方法

**这份方法的每一条都来自一次实测失败，失败原文附在规则后面。看到 ⚠️ 的地方是已经踩过的坑。**

---

## 先判形态：不同形态的产品，能拿到的东西完全不同

⚠️ **实测风险**：本方法的实测案例集中在少数几个产品（自助 SaaS + 开发者工具），它们恰好都有带索引的文档站、恰好都按用量计费、恰好在某个评分站有足够评论。**换一个形态，一半的取证通道会直接断。**

**开工第一件事：判形态，然后按形态选通道。**

| 形态 | 识别特征 | 能拿到 | 拿不到，改问什么 |
|---|---|---|---|
| **自助 SaaS** | 定价页有具体数字、可自助注册 | 定价九项、额度经济、用户旅程 | — |
| **开发者工具 / API** | 有 API 文档、有 SDK 或包 | 端点结构、限额、包下载量、GitHub | 界面截图常缺（无 UI） |
| **开源 / 开放核心** | 有公开仓库与许可证 | **LICENSE 全文定位付费墙**、许可证变更史、仓库指标、自托管 vs 云的边界 | 收入几乎不可查，改问"付费墙画在哪、为什么还有人付钱" |
| **企业销售制** | 定价页写"联系销售"、有 /enterprise 与 /partners | 采购路径、合规资质、案例研究 | **定价九项基本全空** → 见下 |
| **消费级应用** | 有移动端、应用商店有量 | 评论数与评分、版本节奏、榜单位置 | 文档常很薄，模块要从商店描述与截图反推 |
| **平台 / 市场** | 有供需两侧、有开发者生态 | **供给侧上架速率**、类目结构、抽成（在 API 文档里） | **需求侧本质测不到**，要明说；顶级路径可能属于卖家 |

### 平台 / 双边市场专用打法（第 2 步与第 3 步的分支）

**单边数据无意义，但两侧的可测性完全不对称——先接受这一点。**

1. ⚠️ **顶级路径可能属于卖家。**`/pricing`、`/security` 返回 200 也可能是某个店铺，**状态码分不出来**。每个 200 页面看 `<title>` 与页面结构确认归属（**C-38**）
2. **供给侧规模不在 sitemap 里。**去 `robots.txt` 的 Sitemap 声明里找 **RSS / 最新上架** feed，用 `条数 ÷ 时间跨度` 算上架速率——**这是少数能从外部拿到的硬指标**（**C-39**）
3. **抽成的取证顺序是：API 文档 → 帮助中心 → 卖家协议 → 最后才是定价页。**搜 `fee`、`payout`、`commission`、`take rate`。⚠️ **单个百分比不等于总抽成**，先确认它适用于哪个场景（**C-40**）
4. **需求侧要显式声明未测。**整站流量混着买家、卖家、以及卖家自己带来的访问，**不能冒充买家规模**（**C-42**）

⚠️ **正确的表述形状**：供给侧涨而需求侧不明时，写"供给侧在快速扩张，需求侧无法验证"，**不要合成一句"平台在增长"**。

### 开源 / 开放核心专用打法（第 3 步的分支）

**定价解剖从 `LICENSE` 全文开始，不是从定价页开始。**

1. **读 LICENSE 全文**，不是看 GitHub 页面显示的许可证名——**页面只显示一个名字，看不出有没有目录例外条款**。搜 `Portions`、`directory`、`Commercial` 三个词。开放核心产品会在这里写明**哪几个目录属于商业授权**——那就是付费功能清单（**C-32**）
2. **查 LICENSE 的提交历史**，看方向是收紧（开源→BSL/商业）还是放开（商业→MIT）。⚠️ **许可证变更常夹在普通重构提交里，标题不提**（**C-34**）
3. **调 GitHub API 时注意 301**——意味着改过名或换过组织，往往伴随定位变化（**C-33**）
4. **代码全开时，付费墙在托管边界上**：比较商业域名与仓库 `homepage` 字段，常是"云产品"与"自托管文档站"两个站（**C-35**）
5. **仓库指标要剔除机器人**，看前 10 人的提交占比而不是贡献者总数（**C-36**）

⚠️ **robots.txt 干净在开源产品上的含义不同**：增长靠仓库与文档，不靠折扣落地页，所以没什么要藏——**不要按 C-03 解释成"没有隐藏折扣"**（**C-37**）

### 企业销售制专用打法（定价拿不到时）

**不要因为没有定价页就跳过商业模式这一节。**改问：

- **采购路径**：要不要 demo、有没有 POC、合同期多长——从 `/enterprise`、`/request-demo` 表单字段反推（问公司规模、预算、时间线的表单，说明它按这几项分层）
- **第三方采购平台**：AWS / Azure / GCP Marketplace 常有**公开的合约价与计费单位**，这是企业软件最容易被忽略的公开价格源
- **软件评测站的定价 tab**：G2、Capterra、TrustRadius 常收录用户自报价格区间
- **合规资质**：SOC2、ISO、HIPAA、GDPR 页面——**有哪几张证书，直接说明它卖给哪个行业**
- **招聘岗位**：在招哪个行业的解决方案工程师、在招哪个地区的销售，就是它在攻哪个市场
- **案例研究**：企业销售制产品通常**有**详细案例（这是它唯一的公开销售材料），要逐个读，从中反推客单价与实施周期

### 通道断了怎么办：三条降级阶梯

**文档索引**（按顺序试，不要假设第一条存在）：
`llms.txt` → `sitemap.xml` → 文档站侧边栏 → OpenAPI/Swagger 规范文件 → Postman 公开集合 → GitHub 仓库的 `docs/` 目录 → 帮助中心的搜索页与分类页 → 官方 YouTube 频道的播放列表标题

**口碑源**（按可达性排序，前两个经常被拦）：
G2 / Trustpilot（常 403）→ **SourceForge / Capterra / GetApp**（较易取）→ Product Hunt 讨论区 → Reddit 与 Hacker News → **YouTube 评测的评论区** → 官方社区或 Discord → 应用商店评论 → 官方 FAQ 与故障排查页的标题（**厂商自己写的故障清单**）

**规模代理**（按形态选，至少凑两条）：
Tranco 排名（任何有网站的产品都适用）→ 应用商店评论数 → 仓库指标 → 包下载量 → 第三方 ARR 估算 → 融资规模

## ⚠️ 关于本方法里的实测案例

**所有"⚠️ 实测…"都是"曾经这样失败过"的记录，不是"目标产品应该有这些东西"的清单。**

看到"实测某产品有 25 个视觉模板"，**不要去找 25 个模板**；那条要传达的是"模板库的构成能反推它认定的客户在做什么"。

### ⚠️ 举例串味：本文档里的例子会被当成本次的发现写进报告

**举例天然会污染输出**——写得越具体、越像发现，越容易被整段搬进报告。跨模型实测已复现两次，见案例库 **C-28**。

**硬规则：**

- **报告里的每一个状态码、路径、数字、公司名，必须能指回本次实际取到的证据。**指不回去的删掉，**不要"看起来合理就留着"**
- **本文档里出现过的产品名与域名**（scrapecreators、Blotato、repurpose.io、OpusClip、Ayrshare、Zernio、Postiz、n8n 等）**要格外警惕**——它们最容易被无意识地搬进报告
- **交付前跑 `node scripts/check-report.mjs <报告.md>`**，它按契约逐条验完成度，并挑出串味、内部术语、工作日志、内联 HTML

⚠️ **不要简化成"这些名字一律不许出现"**——硬禁令会逼着作者删掉真实证据，比串味更糟（见 C-28 的"不适用于"栏）。

**判据是证据，不是名字**：这个名字后面跟的数据，是本轮取到的，还是从这份文档里搬的？**前者留，后者删。**检查器只负责标出来让人逐条确认。

再举一例：看到"实测额度极差 1,250 倍"，**不要假设新产品也按额度计费**；那条要传达的是"计价单位背后可能藏着一个数量级的成本差异，要去算"。

**方法是问题清单，案例只是问题为什么值得问的证据。**

## 这个包怎么组织的（先读这段，30 秒）

**这份文档是唯一入口。**任何产品调研、竞品分析、赛道判断的任务都从它开始。

它下面挂着四个子方法。**不需要调用方去挑、也不靠关键词猜——本文档会在指定步骤点名要谁：**

| 走到哪一步 | 加载谁 | 它负责什么 |
|---|---|---|
| 第 0 步 开工前 | `research_viewpoint` | 定视角（买 / 做 / 投 / 管），决定后面哪几节写满 |
| 第 3 步 赛道 | `market_landscape` | 竞品门禁、规模口径、空位与威胁排序 |
| 第 7 步 口碑 | `customer_proof` | 客户画像、逐字引文纪律、评价平台的偏差 |
| 第 8 步 变化 | `last_30_days` | 近期动态的取证与时间标注 |

**只有本文档会被关键词路由命中，四个子方法不会。**这是刻意的：以前它们和本文档抢"竞品""定价""赛道"这些词，同一个请求可能落到某个子方法上，绕过整套流程。

**所以用法只有一句话：给一个网址（或产品名 + 视角），加载本方法，剩下的按下面的顺序走。**

## 执行顺序（先看这个，再看规则）

规则是用来判对错的，顺序是用来干活的。**按下面的顺序走，不要跳步。**

某一步的通道被拦时，按该步自己的降级路径换通道（见第一节状态码三分类、第三节四级降级），**不许跳过。**

```
0  判视角        采购者 / 创业者 / 投资人
                 → **先加载 research_viewpoint**，这一步不做完不许往下走
                 ↓ 决定后面哪些节写满、哪些从简

1  先拿路径空间   sitemap.xml / llms.txt / robots.txt  ← 这一步必须在探测之前
                 ⚠️ llms.txt 有三种物种：营销文案 / 文档索引 / 给代理的路由契约。
                 **读之前先判是哪一种**——营销型的内容进宣称清单，不进事实（C-41）
                 ⚠️ 实测：某产品在裸域上探 20 个标准路径，19 个 404，看起来像单页站；
                 而 sitemap 里有 334 个 URL。**先探测后拿清单，会得出完全错误的结论。**

2  站点清点      按第 1 步拿到的真实路径空间去探测，补探标准路径与子域
                 apex 与 www 都试，跟随重定向，记 200 / 404 / 被拦 三类
                 ⚠️ **多语言站的路径带 locale 前缀**（/en/pricing、/zh/pricing），
                 裸路径会全部 404 —— 实测踩过

2.2 读 robots.txt 的 Disallow 清单  ← 情报密度最高的一个文件
                 它不想被索引的东西，往往正是它的真实商业动作
                 ⚠️ 只读清单不抓取——读清单是它的用途，抓取不是

2.5 索引逐条点开  索引里凡涉及定价、额度、限额、配额、错误码的页面，逐个点开
                 ⚠️ 列出来不等于读过——这是踩过最贵的一个坑

3  一手取证      定价页 → 文档 → 客户页 → 条款正文 → changelog → status
                 每条事实记 URL + 逐字引文 + 时间

3.5 产品说明书   功能模块表（业务语言）+ 用户旅程 + 界面截图 ≥3 张 + 差异化判定
                 ⚠️ 端点清单是证据，功能模块才是产品（见一·五节）

4  宣称清单      从首页抄下所有宣称，逐条回到第 3 步的证据里找对应
                 冲突显式列出

5  公司底盘      检索融资 / 员工 / ARR；再做三角验证（npm / GitHub / App 评论数）
                 三条独立信号才能升为高置信

6  赛道扫描      品类无关查询找 5–8 家 → 每家开它自己的官网 → 归一化比价
                 → **先加载 market_landscape**（分层、门禁、规模口径都在它里面）
                 ⚠️ **先分层再比较**：这些玩家干的是同一件事吗？按"输入→输出"切段
                 ⚠️ 比价前先确认交付同构

6.5 规模与格局   Tranco 排名 + 30 天趋势（全部竞品）→ 相对位置与格局判断
                 ≥2 个代理维度；写清口径与失真方向
                 ⚠️ 分层结论必须每层都有可信区间内的锚，全靠长尾撑的层写"证据不足"

7  口碑取证      ≤10 条逐字引文，正面/负面/建议三类，带来源与日期
                 先引文后总结，takeaways 必须指回具体引文
                 → **先加载 customer_proof**
                 ⚠️ 不许交总结代替引文，不许写"待测"

8  近期变化      近 30 天：发布、定价变动、融资、事故、用户反应
                 → **先加载 last_30_days**
                 ⚠️ 这一步我漏过三轮——skill 存在但执行顺序里没有它，等于没有

9  纵向对比      Wayback 快照对比定价页与首页文案，看它怎么变过来的

10 判断成文      开篇写不用术语的 200 字摘要 ← 先写这个
                 每一节以"所以"收尾；标置信度；写证据缺口
                 取证过程（状态码、接口、探测细节）挪附录或删
```

## 每一步的完成标准 → `contract.json`

⚠️ **实测失败（两次，同一个病）**：执行顺序有了，但走到第 5、6 步就停了，客户与竞品两节直接写"本轮未做"——**"未做"被当成了合法交付**。后来把标准写成表格放在这里，**还是漏**：截图漏 2 轮、近 30 天漏 3 轮、宣称清单整步跳过而无人察觉。

**根因不是标准不清楚，是散文没有执行力。**这份文档有 69 处"必须／不许／至少"散落在 63 个章节，靠人记得去逐条核对——**记不住是必然的，不是意外。**

**所以完成标准不再写在这里。**它的唯一真相源是 `skills/product-research/contract.json`，由代码执行：

```bash
node scripts/check-report.mjs <报告.md> [--manifest <证据清单.json>]
```

⚠️ **不要在本文档里重复契约里的数字。**重复的副本一定会不同步——这已经发生过。**要改标准就改 `contract.json`。**

**本文档负责回答"为什么"，契约负责回答"够没够"。**

### 关于证据清单（manifest）

有些要求从交付文本里看不出来：探了几个路径、读了几个客户案例、有没有翻过官方视频频道。**这类检查的是调研过程，不是交付物，只能由调研方声明。**

清单是与报告同名的 `<报告>.evidence.json`，**独立文件，不进交付物**：

```json
{
  "pathSpace": ["sitemap.xml: 223 URLs", "robots.txt: 7 Disallow", "llms.txt: 404"],
  "probedPaths": ["/pricing 200", "..."],
  "caseStudiesRead": ["...2026-05", "...2026-03", "...2025-11"],
  "videoChannelChecked": "youtube.com/@xxx，25 条标题已过",
  "skipped": { "case-studies": { "reason": "absent", "note": "站点无案例页" } }
}
```

**豁免只有三种理由，写别的一律判为未达标：**

| 理由 | 含义 |
|---|---|
| `blocked` | 通道全部被拦——降级阶梯逐级试过并失败，写明试了哪几个、各报什么错 |
| `absent` | 对象不存在——例如无移动端就没有应用商店评论 |
| `incapable` | 环境不具备该能力——**必须实际试过并失败，写明命令与报错** |

⚠️ **`incapable` 被滥用过五轮**：截图一栏连续五份报告为空，理由都是"环境无渲染能力"，**而一次都没试过**。第六轮一试就成了。**"环境做不到"是一个需要证据的断言，不是可以随手用的豁免。**

⚠️ **"没劲了""预算花完了"不在其中。**预算不够应当缩小范围（少查一家竞品），**而不是每一项都做半截。**

## 三道闸门

**闸门 A（开工前）**：视角判定完了吗？站点清点完了吗？**文档索引里和定价/额度相关的页面全点开了吗？**没做完不许进入检索。

**闸门 B（动笔前）**：公司底盘六项有没有？拿不到的做过三角验证吗？宣称清单逐条核过了吗？竞品是否都开过它自己的域名？

**闸门 C（交付前）**：跑第十节的自检 12 条。**任何一条"待测""建议自行试用"都要回到第 7 步。**

## 零之一、写给谁看：术语纪律

⚠️ **实测失败（用户原话）**："你写的东西，其实很多东西是人看不懂"。

前几轮报告里出现过 `NOASSERTION`、`llms.txt`、"API 端点分组"、"状态码三分类"、"服务端渲染"。**这些是我取证时的工作语言，不是读者的语言。**读者是产品经理、投资人、业务负责人——他们要判断，不要看我的施工过程。

### 三条硬规则

**一、任何技术术语第一次出现，必须紧跟一句人话。**

> ❌ "GitHub 返回 license: NOASSERTION"
> ✅ "它的开源许可证连 GitHub 都识别不出来——因为那不是标准开源许可，而是自定义的限制性协议，**限制别人拿它的代码去做商业分发**"

**二、报告开头必须有一段"不用任何术语的摘要"**，长度控制在 200 字内，让完全不懂技术的人读完知道：这东西是什么、卖给谁、赚多少钱、现在处在什么位置、最大的机会和风险各是什么。

**三、取证过程不进正文。**我怎么探测路径、用了哪个接口、状态码是几——这些放附录或直接不写。**正文只写发现和判断。**

⚠️ 判据：**把报告给一个不懂技术的人读，他能不能复述出三条结论？**复述不出来就是写给自己看的。

### 可读性五条（用户原话："整体报告可读性非常差"）

**⚠️ 这五条每一条都对应一次真实的差评。**

**一、图必须嵌入，不能给路径。**
⚠️ 实测：找到 19 张截图，报告里只列了文件路径。**而那些路径实际是 404**——内部相对路径，外部取不到。**列一串死链当证据，比不写更糟。**
规则：能嵌就嵌（Markdown 图片语法，先验证 URL 返回图片类型）；**取不到就一句话说明"本轮环境无渲染能力，无法提取截图"，不要列路径充数。**

**二、⚠️ 与证据等级标记不进正文。**
⚠️ 实测：正文里满屏 ⚠️ 和"三方估算/未核实/中置信"，读者要绕过我的认知过程才能读到内容。
规则：**正文只在结论确实不可靠时用一次限定词**（"据三方估算"）；完整的证据等级表放**单独一节或脚注**。

**三、不许在正文里跟自己对话。**
⚠️ 实测：正文里出现"v2 说错了""外部评审指出""我上一版写…是错的"。**这是我的施工日志，读者不关心。**
规则：版本差异、自我更正、方法反思**全部放最后一节**，正文只写当前结论。

**四、表格不许裸放。**
⚠️ 实测："2.4 差异化 vs 标配"直接甩一张表，用户原话"写的没头没尾，不知道你在说什么"。
规则：**每张表前一句引子说这张表要回答什么，表后一句"所以"给判断。**每节开头一句话说本节回答什么问题。

**五、结论在前，证据在后。**
同一节里先给判断，再给支撑。**不要让读者读完三段证据才知道你想说什么。**

**六、同一张表里不许出现方向语义相反的相邻列。**
⚠️ 实测：排名表里"排名"列是数字越小越好，紧邻的"30 天变化"列却是正数越大越好。用户直接读反了，把"前进 16 万位"读成"后退 16 万位"。**这不是读者不细心，是表格设计错误。**

规则：**任何"变化量"列要么写成文字方向（"前进 N 位""后退 N 位"），要么直接给前后两个值让读者自己比。**不许只给带符号的差值，尤其当同表另一列的方向是反的。

同理适用于：排名、名次、耗时、错误率、跳出率——**所有"越小越好"的指标，它们的变化量都是这个陷阱。**
同一节里先给判断，再给支撑。**不要让读者读完三段证据才知道你想说什么。**

判据：**通读一遍，任何一段如果读者会问"你到底想说什么"，就是这一段的结构错了。**

## 零、举证责任在数字这一侧

用户自己能看见首页。**把首页换个说法重排一遍，价值是零。**有价值的只有他自己点十分钟点不出来的东西。

每一个**外部事实**（价格、数字、日期、客户名、竞品能力）要写进报告，必须同时具备：

1. **完整可点开的 URL**——不是"官网"、不是"文档"、不是机构名
2. **逐字引文**——能在那个页面上原样找到的片段，且包含那个事实本身
3. **本轮的获取时间**

**三者缺一，这条不写。**不是标成"待确认"，是不写；或者按第六节降级成"候选，未验证"。

核心判据一句话：**你能把那句原文一字不差地写出来吗？**写不出 = 你没真的打开那个页面 = 这是你回忆出来的 = 不许写。

### 一律视同无证据的四种写法

⚠️ 全部是实测中真实出现过的：

- **编造一个看起来合理的 URL。**标准路径的命名太有规律，「合理」与「存在」几乎无法区分——见 **C-31**。实测中模型造出并连续三轮重试同一个死链。**只允许打开搜索结果里出现过、或当前页链接里出现过的 URL。**
- **把没打开过的产品写进竞品表。**实测十六轮里反复出现：读的是 Productboard 和 ProductPlan，报告里写的却是 Jira、Asana、ClickUp、monday dev。**品牌先验会压过指令，这条必须靠证据要件挡，不能靠自觉。**
- **把搜索摘要当事实。**实测一份报告 16 个来源里 15 个只是搜索摘要，"平均响应 3.12 秒""成功率 98.2%""20+ 平台"全部没打开过页面。**摘要是线索，不是证据。**
- **给了很具体的来源名和很具体的数字，但没有 URL。**具体不等于真实，越具体越要验。

### ⚠️ 证据标准必须对称

**这是外部评审抓到的、我自己没发现的失效**：同一份报告里，对目标产品的每个数字都打上"厂商宣称，未核实"，**对竞品的数字却照单全收**——Buffer 的 "$22.5M ARR、74 人"、OpusClip 的 "$68M 融资、$10.3M ARR" 直接进表当事实，没标来源、没标日期、没标口径。

而这两条恰恰是"分发层不值得进、生成层烧钱"这个核心结论的地基。**地基没标来源，上面盖的楼全是悬空的。**

**规则：竞品的数字和目标产品的数字，适用同一套举证要求。**第三方估算站（getlatka、Tracxn、CB Insights 之流）给的 ARR 与员工数是**推测值**，必须标明来源、口径日期，并且不许拿来支撑主结论——只能当旁证。

### ⚠️ 每条结论标置信度，"未发现"不等于"不存在"

**同样是外部评审指出的。**路径 404 能证明的是"该路径不存在或不可访问"，**不能证明整个站、注册流程、法务页面都不存在**。

四级标注，写进报告：

| 级别 | 判据 | 写法 |
|---|---|---|
| **观察事实** | 本轮亲自取到 | "官网无公开 status 页"（已探测 17 个路径） |
| **高置信推断** | 多条独立证据指向同一结论 | "无对外 SLA" |
| **中置信推断** | 单条证据 + 合理推理 | "公开信息显示团队极小" |
| **低置信推断** | 只有间接迹象 | "法务可能尚未规范化" |

⚠️ 实测反例：把"无团队页 + 无招聘页"直接写成 **"实质单人"**，然后整节"单人依赖是最大风险"建在这个未证实的前提上。**正确写法是"公开信息显示团队极小（中置信）"**，除非有第三条独立证据。

### ⚠️ 拿不到官方数据时，做三角验证，不要停在推断

外部评审指出的缺口。⚠️ 实测有效的免费旁证通道：

- **npm 包的发布者与月下载量**——发布者账号能反推谁在做工程；下载量是用量下限。实测某产品的官方集成包月下载 3,128，发布者账号是创始人本人的账号
- **GitHub 组织的公开成员数与提交作者**——实测 Blotato-Inc 公开成员 0、全部提交作者为创始人，与 npm 发布者互相印证
- **GitHub 组织创建时间**——实测 2025-01，与二手数据库记的"成立 2018"矛盾，这条矛盾本身要写进报告
- **仓库最近提交时间**——**没有 changelog 时，这是迭代速度的替代信号**
- **App Store 评论数**——用户基数的下限
- SimilarWeb 流量档位（付费）

**三条独立信号指向同一结论，才配从"推断"升级为"高置信"。**

⚠️ **三角验证清单依赖产品形态，不是万能的。**实测 Gamma（消费级 SaaS）：npm 无官方包、GitHub 无可定位组织，**上面这套通道整个失效**。按形态换通道：

- **开发者工具/API 产品** → npm 发布者与下载量、GitHub 组织与提交
- **消费级/团队 SaaS** → App Store 与 Google Play 评论数、Trustpilot 评论量、LinkedIn 公司页员工数、招聘平台在招岗位数
- **开源产品** → 仓库 stars/forks/贡献者/提交频率
- **任何形态** → Wayback 快照的定价页变更史（能看出涨价与改档）、媒体报道的融资轮次

**先判形态再选通道；一套通道跑不通不等于验证不了。**

## 一、先清点，再检索

**目标站自己的页面是密度最高的证据源，优先穷尽它，再向外找。**

⚠️ 实测反例：一轮调研只读了 2 个页面，其中一个还是聚合站，却花掉了全部对外检索额度——**顺序错了，不是预算不够**。（该环境下抓页比检索便宜；换个环境成本关系会变，但"先穷尽目标站再向外"这个顺序不变，因为它与成本无关，与证据密度有关。）

拿到 URL 后，第一件事是把这个站自己的东西扫一遍，不要先去搜。标准路径至少包括：

```
/pricing  /docs  /changelog  /customers  /security  /careers  /about
/status  /terms  /integrations  /blog  /api
docs.  api.  developers.  help.  status.  （子域）
```

⚠️ 实测 linear.app 这 11 个路径全部返回 200，全部免费可读；而同一轮调研只读了 4 到 6 页，却烧掉 4 次检索。

### ⚠️ 404 页面本身要读：结构化数据里常常挂着公司底盘

SEO 插件会把 Organization 的 JSON-LD **注入每一个页面模板，包括 404 模板**。实测一次 404 探测拿到了公司底盘整节的材料，见 **C-02**。

**做法：**

- **任何一次抓取（哪怕返回 404）都先在 HTML 里搜 `application/ld+json`**，再决定这一页有没有价值
- 重点看 `Organization` 块的 `numberOfEmployees`、`foundingDate`、`address`、`description`、`sameAs`（官方社媒矩阵，可直接拿去查 YouTube 频道与视频）
- ⚠️ **这是厂商自己写的**，`description` 里的份额、客户数属于**宣称**，要进第三节的宣称清单，不能当事实

**判据：拿到 404 不等于这一页没东西。先看有没有 JSON-LD，再决定丢不丢。**

### 状态码要分三类，不能只看"是不是 200"

⚠️ 这三条都是手工跑五个产品时当场撞到的：

- **301 / 308 是"有"，不是"没有"。**实测某产品的 `/pricing` 返回 308，跟随后的 `www.` 版本是 200。**apex 域和 www 都要试，重定向跟到底，记最终 URL。**见 **C-08**。
- **403 / 401 / 429 是"被拦"，不是"不存在"。**实测 repurpose.io 的全部 14 个路径都返回 403，换浏览器 UA 仍然 403。**如果按"缺席即证据"去判，会得出"这个产品什么都没有"的完全错误结论。**
- **被拦要换一条抓取通道再判。**实测同一个 `repurpose.io/pricing`，curl 拿不到，换一个抓取器直接拿到了完整四档定价。**一个通道失败不等于拿不到。**
- **200 也不等于拿全了。**实测某定价页返回 200、正文完整，但价格全部由脚本渲染，抓下来一个数字都没有。**关键页面拿到 200 之后还要渲染一遍，见第一·五节第三·五条。**

只有确凿的 **404** 才进下面的"缺席"推断。

### robots.txt 的 Disallow 清单是最高密度的情报源

⚠️ 实测见 **C-03**（含"企业销售制的 robots.txt 通常很干净"这一反向情形）。典型的 Disallow 清单长这样：

```
/offer/ocr-lifetime-deal
/offer/ai-marketer-60-off-monthly
/offer/madgicx-ai-marketer-25-off-monthly
/offer/madgicx-ai-marketer-150-off-quarterly
/offer/madgicx-ai-marketer-500-off-annually
/offer/madgicx-ai-marketer-77-off-first-month
/free-demo   /demo-trial   /products/agency
```

**从 URL 命名本身就能推出三件事**：它在跑大幅折扣（六折、首月 77% off）、有终身买断方案、年付能在官网折扣之外再减 500 美元。

**把它和官网价并排看，才是这条的价值所在**：官网年付已经省 30%，中间档年付约 1,900 美元，而"再减 500"是在这个数上再砍四分之一。**官网价是明码标价的，但它不是真实成交价。**

**所以这条不是用来找隐藏价格的，是用来判断"官网价与成交价差多少"的。**结论对采购者是"进门前先问折扣"，对创业者是"这家在用渠道折扣冲量"。

**通用规则**：`robots.txt` 的 Disallow 列表是**它不希望被搜索引擎看到的东西**，通常包含：促销与折扣落地页、试用与 demo 漏斗、按渠道定制的报价页、已下线但仍可访问的旧产品、内部工具。**这些恰恰是真实商业动作。**

⚠️ **纪律**：读 Disallow 清单可以（robots.txt 就是给人和机器读的），但**不要去抓取它标记为 Disallow 的页面**。URL 命名本身通常已经够用。

### 多语言覆盖的差异本身是情报

⚠️ 实测发现：某产品 sitemap 里有 20 个语言版本，但**只有 en 与 zh 两个语言有完整产品页（解决方案、博客、核心功能页）**，其余 18 个语言只有免费工具页。

**这说明：那 18 个语言的存在目的是免费工具的 SEO 获客，不是真的做那些市场。**真实主战场只有两个。

**通用判据**：把 sitemap 按语言分组，比较各语言的路径种类数。**种类数差异揭示真实市场优先级**，比官网上写的"服务 200 多个国家"可信得多。

### 缺席即证据

⚠️ 实测 scrapecreators.com 的 `/pricing`、`/customers`、`/careers`、`/security` **全部 404**。这四个"没有"合起来是一个明确结论：小团队、没有企业销售动作、不打大客户。

**探测不到的路径要记下来并在报告里用上，不是忽略掉。**没有安全合规页 = 不做企业生意；没有招聘页 = 团队极小；没有客户页 = 还没有可公开的客户。

检索次数留给官网给不了的东西：竞品是谁、第三方怎么评价、融资和团队规模。

## 一·五、产品说明书（人话版）← 前几轮完全缺失

⚠️ **实测失败（用户原话）**："连一个产品最基本的产品功能架构，或者是功能模块的一些介绍什么的都没有"。

前几轮我写的是 **API 端点分组**——那是工程视角，产品经理看不出"这产品长什么样、怎么用"。**端点清单是证据，功能模块是产品。**

### 一、功能模块表（必交付）

每个模块一行，用业务语言，不用技术语言：

| 模块 | 它解决什么问题 | 给谁用 | 关键能力 | 所属档位 |
|---|---|---|---|---|
| 例：内容生成 | 不用自己写文案和做图 | 创作者 | 主题→成品图文/视频 | 全档，按用量计费 |

**模块划分的依据顺序**：产品导航与设置菜单 > API 端点分组 > 定价页的功能列表 > 文档目录。**前者最接近用户认知，后者最接近工程实现。**

### 二、核心用户旅程（必交付）

**从注册到第一次产生价值，一步一步写下来**，标出每一步的摩擦点：

```
注册 → 连接第一个账号（授权流程几步？会失败吗？）
     → 第一次生成（要填什么？等多久？）
     → 第一次发布（要不要审核？失败怎么提示？）
     → 看到结果（有没有数据反馈？）
```

**摩擦点有两个来源，优先第一个：**

**① 厂商自己的 FAQ 与故障排查页的标题。**⚠️ 实测发现：某产品 FAQ 的问题标题本身就是一份完整故障清单——"我的屏幕是空白的只显示…""教程里的选项不存在""点了新建但草稿是空的""显示已发布但平台上没有""帖子显示 CANCELED 是失败了吗""排期按钮是灰的点不动"。**这是厂商自己记录下来的、用户真实撞过的墙，比用户评论更全、更早、更具体，而且免费。**

**② 负面评论里的具体卡点**，按出现频次排。

**两者都不许凭空写。**⚠️ 实测例子：某产品的口碑里有"平台更新后需要反复重连授权"——**这就是旅程第二步的真实摩擦，比任何功能列表都有信息量。**

### 三、界面与截图（必交付，至少 3 张）

**先自己截，截不到再去找。**

⚠️ **"我这个环境做不到"这句话，在真的试过之前不许写。**实测连续五轮以"环境无渲染能力"留空截图，第六轮一试就成了。见 **C-05**。

**取图顺序：**

1. **自己开浏览器截**——公开页面（首页、定价页、功能页、案例页）全部可截
2. **本机浏览器无头模式落盘**——要嵌进报告的图必须是磁盘上的真实文件，只在会话里看到的截图嵌不进去
3. **文档站/帮助中心的界面图**——真实 UI，优先于营销页
4. **⚠️ 登录墙后的界面，去厂商自己的视频里抽帧** ← 见下

### 三·二、登录墙不是墙：厂商自己的视频里全是真实界面

厂商自己的教学视频是**成本最低的真实 UI 来源**——它必须录屏才能教用户。见 **C-05**；⚠️ 并非所有视频都有录屏，先做缩略图矩阵确认。

**做法**（本机装了 `yt-dlp` 和 `ffmpeg` 就能跑，先确认再说做不到）：

```
1. 列频道：yt-dlp --flat-playlist --print "%(id)s | %(title)s" <频道URL>/videos
2. 下单条：yt-dlp -f "best[height<=720]" -o v.mp4 <视频URL>
3. 抽帧：  ffmpeg -ss <秒> -i v.mp4 -frames:v 1 -q:v 2 out.png
```

**先读标题列表，再决定下哪条。**标题本身就是情报：

- `How to connect your...` 这类上手教程 → **真实主界面**
- `NEW in...` `Introducing...` → **最新功能的界面，比官网新**
- 时长最长的那条通常是完整演示

⚠️ **视频不一定在 YouTube**，且一个源被拦不等于拿不到——先从页面 HTML 找嵌入源再按源选工具，见 **C-06**。

⚠️ **视频里能看到官网和文档都没写的能力。**实测两次从演示视频里发现了完全没有对外宣传的核心集成能力——这是任何静态页面都拿不到的。

**频道视频列表本身要过一遍**，当作 changelog 用：发布节奏、最近在推什么功能、哪个功能配了多条视频（配得多 = 它认为难用或重要）。

**图必须真的嵌进报告，用相对路径指向本地文件。**⚠️ 实测失败：曾把外站图片链接和只有内部才能访问的路径写进报告，渲染出来全是破图。**给不出能打开的图，就写明"无图"，不要给一个链接假装有图。**

每张图要写清：这是哪个模块、图上能看到什么、支持了哪条判断。

⚠️ **营销页展示的界面是厂商挑过的，要标注**。它挑哪一屏放首页本身是情报——**它想让你用什么指标衡量它，就会把那个指标放在第一屏。**

⚠️ **版权纪律**：Mobbin、Page Flows 这类界面截图库**有版权且无 API，是人工参考，不是数据源，不能转发给客户**。竞品 UI 截图用于对比评述通常属于合理使用，但**要嵌链、不要拷贝存储**，且必须标注来源页面。

### 三·五、⚠️ 静态抓取拿到的 HTML ≠ 页面上的内容

⚠️ 实测直接写出过一条错误结论：静态抓取拿到零个价格，据此写"定价页不给数字"，而浏览器打开后七档价格全在页面上。**把"我没抓到"当成了"它不给"。**见 **C-04**。

**规则：**

- **凡是"某页面上没有 X"这类结论，必须用浏览器渲染后确认**，静态抓取的缺失只能说明"静态 HTML 里没有"
- **交互控件必须逐个操作**——下拉框、档位切换、月付/年付开关、地区选择。**每个选项都可能对应一组不同的数字**，只看默认值等于只看了七分之一
- **价格、额度、限额这类关键数字尤其危险**——现代站点普遍用脚本渲染，是静态抓取最容易漏的一类

**判据：如果一个页面静态抓取下来"什么都没有"，那大概率不是它没有，是你没渲染。**

### 三·六、成熟度判据（必交付一句话结论 + 两条支撑）

**结论只有三档**：**生产可用 / 早期可用 / 演示阶段**。判据如下，逐条看有没有：

- **文档厚度与最后更新时间**——文档薄的产品，宣称的能力通常是纸面的
- **API 与 webhook 是否存在、有没有版本管理**
- **有没有 status 页与历史事故记录**
- **有没有安全合规页**（SOC2 / HIPAA / GDPR / ISO）——**有就是在打企业客户**
- **changelog 的节奏**——周级 / 月级 / 季度级 / 已停更。**停更比没有 changelog 更糟**
- **移动端**：应用商店的版本号、更新日期、评分、**评论数**（评论数是用户基数的下限证据）
- **企业能力齐不齐**：SSO / SAML / SCIM / 审计日志 / 权限模型 / SLA

**收尾要回答**：最能说明成熟度的是哪一项；**哪些宣称的能力在文档里找不到对应**。

### 四、差异化 vs 标配（必交付）

把功能分两类：**同类都有的（标配）** 与 **只有它有的（差异化）**。
⚠️ 判据：**这一项在竞品官网上找不到对应，才算差异化。**凭感觉标的差异化没有意义。

---

## 二、品类判定：五个槽

在说出任何一个竞品名字之前，先把这五个槽填满：

**谁掏钱** / **解决什么活儿、操作什么业务对象** / **工作流从什么输入到什么输出** / **端到端边界到哪为止** / **怎么交付**

"AI 平台""SaaS""自动化工具""抓取 API"是**架构**，不是品类。买家买的是垂直结果时，品类必须点出业务领域和被搬动的对象。

**用文档定，不要用首页定。**首页写的是想让你相信的，文档写的是实际能做的。

---

## 三、宣称与事实的差距 ← 这一格最值钱

**这是整份报告里别人不做、而我们能做的东西。**

做法是两步：

**第一步，从首页把宣称抄成一张清单。**每条记下原话。典型的宣称：无速率限制 / 永不过期 / 秒级响应 / 支持 N 个平台 / 无需信用卡 / 企业级安全。

**第二步，逐条去一手页面找对应。**定价宣称去定价页和条款页；性能宣称去文档和 status 页；能力宣称去 API 文档的端点清单；安全宣称去 security 页。

⚠️ 实测撞见过一次真实矛盾：首页写"信用点永不过期"，另一处一手页面写"信用点 6 个月后过期"。系统当时把两条并排当成事实输出，没有指出它们打架。

**冲突必须显式列出来，不许抹平成一句折中的话。**找不到对应证据的宣称，标成"仅厂商宣称，未在一手页面找到支撑"。

### ⚠️ 主域被全站拦截时，宣称从哪里取

实测 Gamma：`gamma.app` 全部路径对 curl 与抓取器**均返回 403**，导致**首页宣称清单采集不到，第三节整节无法执行**。

这种情况不许直接放弃，按顺序换通道：

1. **Wayback Machine 的历史快照**——首页文案变动不频繁，快照通常够用，而且还额外给出文案变更史
2. **App Store / Google Play 的应用描述**——那是厂商自己写的营销文案，等价于首页宣称
3. **官方社交账号简介与置顶帖**
4. **官方文档站的欢迎页**（子域常不被同一套 WAF 拦）
5. **搜索引擎结果里的标题与描述**（厂商自己写的 meta）

**四条都试过仍拿不到，才写"通道全部被拦"，并在报告开头显著声明本轮无法执行宣称对照。**

## 四、定价解剖

不是"有三档"。必须拿到这九项，缺哪项写哪项缺：

1. **计价单位**——按人 / 按用量 / 按记录 / 按坐席。**这一项就是商业模式本身，也直接说明它为谁设计。**
2. 每档的确切价格，**年付和月付分开写**
3. **每一档相比上一档多了什么**
4. **哪些功能被锁在最高档**（SSO、SAML/SCIM、审计日志、SLA、看板、专属支持）——**这一格对采购决策的影响最大**
5. 免费额度到底能干成什么事（具体到数量）
6. 超额怎么收
7. 有没有年付锁定、是否预付
8. 有没有创业/教育/非营利折扣
9. 定价页写"联系销售"就是企业销售动作，要写进结论

### 跨产品比价前必须先归一化

⚠️ 实测五个同品类产品，计价单位互不相同：Buffer 按**频道**每个 $5/月；Postiz 按**频道打包**，$29 含 5 个频道；Blotato 按**工作区 + AI 额度**，$29 含 20 个账号和 1250 点；Repurpose 按**每个社交网络的账号数**，$35 含每网络 3 个。

**标价不可直接比。**必须先换算到同一个单位（每频道每月多少钱、或用户实际用量下的月成本），否则"$5 起"和"$29 起"这种对比是误导。归一化用的假设要写出来。

### ⚠️ 阶梯定价是分段函数，不许采样几个点就报区间

**这是外部评审抓到的一个真错误。**报告里写"Zernio 在 30–200 账号区间比 Blotato 便宜"——这个区间是看着六个采样点（5/20/40/100/300/1000）目测出来的。

**逐点求解后真相是四段**：1–6 Zernio 便宜、7–20 Blotato、21–26 Zernio、27–40 Blotato、41–280 Zernio、281 打平、282+ Blotato。**两头都错了，中间还漏了一整段。**

规则：**阶梯或分段定价必须逐点计算求交叉点，写出精确边界。**采样点只能用来展示，不能用来下区间结论。这与"矩阵是凑出来的不是算出来的"是同一类错误。

### ⚠️ 比价前先确认两边交付的是同一件事

**外部评审指出的逻辑断裂。**报告在第二节论证了目标产品"生成是主干、分发只是出口"，转头却按"账号数"把它和一个**纯分发、完全不生成内容**的产品放在同一条价格曲线上比，还得出"最该盯着后者"。

**这是拿"内容工厂 + 发布管道"去比"只有发布管道"——便宜的那个只是少了一整层能力。**

规则：归一化比价之前，先确认两边的交付物同构。不同构时，**威胁范围要收窄到"只用重叠那部分能力的客户"**，并在结论里写明这个限定。

### ⚠️ 不许给自己的建议无依据地打难度分

⚠️ 实测自打脸：报告通篇批评别人"无依据的自信"，收尾却写"这个功能建造难度低"——没有任何依据。**要么给出依据，要么写"难度未评估"。**

---

## 五、活跃度、体量与投入方向

全部能从这个域名免费推出来：

- **changelog 的更新频率**——最强的活跃度信号，没有之一。最近一次是上周还是两年前，说明一切。
- **招聘页在招什么岗位**——钱往哪投；没有招聘页说明团队极小
- **status 页的历史事故**——可靠性的真实记录
- **security / compliance 页**——有 SOC2 / HIPAA 就是在打企业客户
- **文档厚度**——文档薄的产品，宣称的能力通常是纸面的
- **App Store / Google Play**——版本号、最近更新日期、评分、评论数
- **融资与团队规模**——官网基本没有，要从媒体报道、招聘页、隐私政策里的法律实体名去挖

## 六、竞品：四道门加一道引文

一个产品要进对比表，四条同时成立，每条都有它**自己域名上**的证据：

1. 相同的经济买家
2. 相同的主要任务和业务对象
3. 工作流的输入、输出、端到端边界可替代
4. 买家真的会拿它替代目标产品来干这件事

**再加一道**：该产品的每一格数据，必须有一段能在它自己那个页面上原样找到的引文。⚠️ 只验域名不验引文是不够的——模型会把第三方文章里看来的信息，挂在一个它确实打开过的竞品域名下。

不满足的归为**相邻**（同买家或同工作流，范围或阶段不同）或**替代**（不同品类、服务、人工流程）。通用 AI 助手、横向自动化平台、代理机构默认是相邻。**自己的理由里出现"互补""上游""下游"，就不是直接竞品。**

### 证据不够时怎么办——价值不打折

⚠️ 实测反复出现的失败模式：验证不了就把整个竞品段删空，用户看到一片空白。**这是错的。**

正确做法：

- 验证过的 → 直接竞品，进对比表
- 只在第三方盘点里出现过的 → **"候选，未验证"**，列出来并说明没验证
- 类别地图照给
- **给判据而不是数值**：「若 X 按坐席计费而非按用量，本品的成本优势不成立」——这种结构性判断不需要知道 X 是多少

---

## 七、口碑

去 G2、Capterra、TrustRadius、Reddit、Hacker News。**正面主题和常见抱怨分成两栏**，各自带来源。

⚠️ 一条轶事不是普遍情绪。实测出现过把某聚合站上 12 条评价写成"用户评价显示高满意度"——这不是信号，是噪音。要么给出评价数量和平台，要么不写。

---

## 八、风险与边界

**这一层是"价值"最集中的地方，也是最容易整段漏掉的。**

⚠️ 实测：ScrapeCreators 的核心风险一句话就能说清——**整个生意建立在 TikTok、Instagram 不封它的前提上**，平台一改反爬策略产品就归零。这个判断从产品定义本身就能推出来，而连续四轮报告一个字都没提。

固定要问的几类：**平台依赖**（命脉握在谁手里）、**单点依赖**（只做一个渠道/一个客户群）、**合规边界**（数据来源的法律灰度）、**文档空白**（宣称有但文档没写的功能）、**锁定成本**（能不能导出、迁移要多久）。

---

## 八·五、试用级证据不许推给用户

⚠️ **这是用户当面指出的失效，也是最严重的一条**：报告最后列了一张"额度消耗待测表"，让用户自己去注册试用、逐项测量。

> **用户找你就是为了不用自己去试。把"待测"写进交付物，等于把活退回去，还收了钱。**

**"我没试过"不是缺口，是没找。**试用级信息几乎总是已经被别人公开过了，按下面的顺序去挖：

### 一、先挖它自己的文档 ← 最容易被跳过

⚠️ 实测重罚：我在报告里写"超额计费官网未说明""1,250 点能生成多少条内容官网没写"，并把它列为待测。**实际上两条都在它自己的文档里，而且我已经把那个文档索引打印出来了，却没有逐条点开。**

- `/api/credits.md` 写着 `pricePer1000CreditsUsd: 6.0` —— 超额价格
- FAQ 里写着"哪些操作扣额度、哪些不扣"
- 还有一整页 `ai-video-credits.md`，**按模型逐个列出单次消耗，并给了官方算例**

**规则：文档索引（`llms.txt`、`sitemap.xml`、侧边栏）列出来的页面，凡与定价、额度、限额、错误码、配额相关的，必须逐个点开。列出来不等于读过。**

### 二、找别人的实测

- **YouTube 评测与实操录屏**——最高价值。评测者会在镜头前展示真实界面、真实用量、真实失败。视频描述与评论区常有补充
- **深度评测文章**——搜 `<产品> review 2026`、`<产品> hands on`、`<产品> vs`，注意区分联盟营销软文与真实实测
- **G2 / Capterra / TrustRadius 的长评论**——常写明公司规模、用了多久、踩了什么坑
- **Reddit / Hacker News / 官方社区**——找"我用了三个月"这类帖子
- **官方 changelog 与博客的实操教程**——常含真实截图与参数

### 三、能免费注册的就注册

免费档或不要信用卡的试用，注册本身就是取证。**不要因为"要注册"就跳过。**

### 四、实在拿不到，给判据不给空表

按第六节：写出"若单次生成成本高于 X，则该定价对高频用户不成立"这类结构性判断，**而不是列一张全是"待测"的表让用户填。**

---

## 八·七、变化比状态更有信息量

⚠️ **实测漏洞**：`last_30_days` 这份 skill 一直在 skill 集里，但主方法的执行顺序里**没有对应步骤，结果连续三轮一次都没用上**。方法没给它位置，它就等于不存在。

**一份只写"现在什么样"的报告，价值远低于同时写清"它怎么变过来的、最近在动什么"。**

### 近 30 天（走 last_30_days）

发布与 changelog · 定价或额度变动 · 融资与人事 · status 页的事故 · 社区里的新抱怨或新赞。**每条要有明确日期**，拿不到日期的不写。

### 迭代节奏（changelog）

**看的不是"有没有 changelog"，是它的节奏**：周级 / 月级 / 季度级 / **已停更**。

⚠️ **停更比根本没有 changelog 更糟**——没有说明它从来不公开，停更说明它公开过然后停了。**最后一条的日期是关键，要写进报告。**

### 纵向变化（Wayback 快照对比）

这一层几乎无人做，而且极便宜：

- **定价页的历史快照** → 涨过几次价、改过几次档位、**有没有悄悄砍掉免费额度**。⚠️ 悄悄砍免费额度是最强的"增长压力"信号
- **首页文案的历史快照** → 它换过几次定位。定位换得频繁 = 还没找到 PMF
- **档位名称的变化** → 出现 Enterprise 档的那一刻，就是它开始做企业销售的时点

### 前瞻信号：从公开物反推路线图

不要只看它说要做什么，看它**已经花钱和花人力在做什么**：

- **招聘岗位的具体职位**——不是"有没有招聘页"，而是在招什么。招销售 = 在推增长；招 SRE = 在补稳定性；招某个垂直行业的解决方案工程师 = 在打那个行业
- **文档页面的最近更新时间**——哪几页最近改了，就是它正在动的地方
- **模板库与示例库的内容**——它给的模板 = 它认为客户要做什么，**这是反推真实用例最直接的一手证据**
- **集成清单的构成**——它接了谁，说明它认为客户的技术栈长什么样
- **API 错误码表**——暴露系统边界与常见失败模式
- **开源产品**：issue 标签分布、最老的开放 issue（技术债与真实优先级）

### 它自己认谁是威胁

⚠️ **极便宜且高价值，之前三轮都没做**：很多产品官网有 `/vs/<竞品>` 或 `/alternatives/<竞品>` 页面。

**它自己建了对比页的那几家，就是它认定的威胁**；页面里它强调的对比维度，就是**它认为自己的优势和对方的软肋**。反过来，**它回避不谈的维度，通常是它自己的短板**。

这比任何第三方盘点都准——**是竞争焦虑的直接证据**。

⚠️ 但按第六节门禁：**对比页里关于对方的数据不可直接引用**（那是它写的），只能用来发现候选和读它的焦虑。

---

## 八·八、法务与商业条款（采购者视角必读）

三轮报告一次都没查过条款正文，只查了"有没有 /terms 页"。**条款里有采购决策必需的东西：**

- **责任限制与赔付上限**——出事赔多少
- **数据归属与去向**——你的数据是谁的、会不会被用于训练
- **SLA 的具体承诺**——可用性百分比、赔付触发条件（很多"企业级"其实没有可赔付 SLA）
- **涨价与变更条款**——能不能单方面改价、提前多久通知
- **终止与数据导出**——停服后数据能拿回来多久

⚠️ 实测：Blotato `/terms` 为 404——**一个处理用户社交账号授权的产品没有服务条款页**，这本身是重大发现，但当时只当成"缺席"记了一笔，没有追问它的授权是在哪里约定的。

## 九、交付底线

### 九·零、每份报告必须带 Mirrival 品牌页眉

**这些报告是要被转发的**，署名要跟着走。

**做法**：把 `skills/assets/mirrival-report-header.md` 整段复制到报告最顶部，替换三个占位符（`{{标题}}`、`{{取证日期}}`、`{{方法版本}}`）。**不要自己写页眉。**

**为什么用内嵌 base64 而不是图片链接**：报告要靠单个 `.md` 文件传播——发给别人、转 PDF、丢进别的编辑器。**引外部图片路径一定会在某一环掉图**，base64 内嵌的 logo 跟着文件走。

### 九·零·一、⚠️ 报告是交付物，不是工作日志

⚠️ **实测失败**：交付的报告里混进了大量只有作者关心的东西——"本报告已修订""初版我写错了""上一轮我完全漏掉""这轮调研过的所有产品里最多""我把没抓到当成了它不给""纪律说明：我没有去抓取 Disallow 页面"。**客户买的是结论，不是我怎么得出结论的过程。**

**一律不许出现在交付物里：**

| 禁止 | 改成 |
|---|---|
| 方法名与版本号（`product_research_method v1.7`） | 不写。页眉只留品牌与日期 |
| 修订自述（"上一版写错了""这一节是修订过的"） | **直接给正确结论**，不留改错痕迹 |
| 第一人称过程（"我没点开""我漏掉了""本轮未做"） | 归入"本报告的边界"表，写**客户受什么影响**，不写我做了什么 |
| 工具与取证细节（状态码、静态抓取、渲染、爬取纪律） | 删掉，或压成一句来源说明 |
| 跨报告的横向自比（"这是调研过的产品里最多的"） | 换成对客户有意义的参照（"在同类工具里属罕见数量"） |
| 内部术语（置信度四级、缺席即证据、形态判定） | 用普通话表达同样的意思 |
| 章节标题里的自评（"← 这一节是本报告的重点"） | 普通标题 |

**"边界"那一节的写法**：不写"我没做什么"，写"**未取得什么 → 对判断有什么影响**"。前者是免责，后者是专业。

**判据：把报告交给一个不知道它是 AI 生成的客户，他能不能看出这是机器写的、看出作者改过几版？**能看出就是没清干净。

### ⚠️ 报告里只用纯 markdown，不许用内联 HTML

⚠️ **实测失败**：页眉第一版写成 `# <img src="data:image/png;base64,..." width="30"> 标题`，为的是控制 logo 尺寸。**用户的预览器不渲染内联 HTML**，于是整串 4,600 字符的 base64 被当作正文，以 H1 字号糊满了一屏。

**规则：**

- **图片一律用 `![alt](src)`**，不要用 `<img>`。**尺寸靠选对分辨率的源文件解决**（页眉用 32px 的 PNG，自然尺寸就对），不要靠 `width` 属性
- **`<sub>` `<br>` `<div>` `<span>` 同理，都不许用**
- **判据：把报告丢进一个只认 CommonMark 的渲染器，是不是还能看？**

**内联 HTML 在很多渲染器里会被原样输出，而 base64 一旦被原样输出就是灾难**——它不是"样式差一点"，是整篇报告的第一屏被毁掉。

⚠️ 页眉里的方法版本要写**当前实际版本**，不要照抄模板里的示例。

---

一份合格的报告至少要有下面这些。**做不到的那项要说明为什么，不许静默省略。**

- **开篇摘要**：200 字内、不含任何技术术语，说清是什么/卖给谁/赚多少/什么位置/机会与风险
- **功能模块表**：业务语言，每模块含"解决什么问题、给谁用、关键能力、所属档位"
- **核心用户旅程**：注册 → 第一次产生价值，逐步写，摩擦点取自口碑引文
- **界面截图 ≥3 张**：每张说明是哪个模块、图上看到什么、支持哪条判断
- **差异化 vs 标配**：判据是竞品官网找不到对应
- **相对市场位置与格局**：Tranco 排名 + 30 天趋势 + ≥2 个代理维度，写清口径与失真方向
- 公司底盘：成立年份、总部、团队规模量级、融资与最新估值、客户规模量级
- 能力：按领域分组，每组有具体条目，来自文档不是首页（模块清单优先取 API 端点分组）
- 定价：第四节九项 + 额度/用量经济（单次消耗与极差）
- 宣称与事实对照表
- 具名客户：组织名 + 具体场景 + 明确公布的结果
- 竞品：已验证的进表，候选的列出来并标注；**附它自己的 /vs/ 页揭示的威胁名单**
- **口碑：≤10 条逐字引文（正面/负面/建议三类）+ 抽样说明 + 建立在引文上的 takeaways**
- **近 30 天变化**：发布、定价变动、融资、事故，每条带日期
- **纵向变化**：Wayback 快照对比出的定价与文案演变
- **前瞻信号**：招聘岗位、文档更新时间、模板库、集成清单反推的路线图
- **法务条款要点**：责任限制、数据归属、SLA 赔付、涨价条款、终止与导出
- 风险
- 决策：谁该选、谁不该选、签字前必须自己核实的三件事

### 篇幅不是约束

⚠️ **实测失败：我给自己设了不存在的限制。**没有人要求报告要短，而我连续三轮把内容往回收，还在方法里塞了长度上限。

**该长就长。**一份有价值的产品调研可以很长，只要每一节都在回答一个真实问题、每一段都带得走一个判断。**判据是价值密度，不是字数。**

**写不完可以分批写再拼装**——先出公司底盘与产品结构，再出定价与口碑，最后出赛道与判断。分批不是降级，是正常做法。

**真正该删的只有一类**：不产生任何决策输入的段落。见下。

### 禁止的压缩方式

- ⚠️ 用"因篇幅限制""后续同理"跳过章节——实测某轮在输出上限还剩三分之二时就用这句跳过了六个模块
- 因为"我觉得用户不关心"删掉某一节
- 用套话填充本该写具体内容的位置
- ⚠️ **交付物里出现"待测""建议自行试用""需要实测"的表格或清单**——见第八·五节。要么去挖二手实测证据，要么给判据
- ⚠️ 明明读了文档，能力清单却是空的——实测多轮出现：读了 docs、features、conceptual-model 三页，`capabilityGroups` 交了空

## 十、交付前自检

0. **Mirrival 品牌页眉带上了吗？**占位符都替换了吗？logo 是内嵌的还是引了外部路径？
1. 每个外部事实都有 URL + 逐字引文 + 获取时间？举不出的已按第六节降级，而不是删空？
2. 随机抽 3 个数字，逐个问「原话是什么、URL 是什么」——答不出即为编造，删掉重写
3. 报告里出现过的 URL，是否都在本轮真实打开过或出现在搜索结果里？**有没有自己造的路径？**
4. 竞品表里的每个产品，是否都打开过它自己的域名？
5. 官网标准路径扫完了吗？**探测到的 404 有没有用进结论？**
6. 首页宣称清单逐条核过了吗？冲突有没有明说？
7. 定价九项逐项过了吗？缺的写明缺了？
8. 风险一节是空的吗？**空的几乎总是"没想"，不是"没有"。**
9. 有没有哪一节是能力清单为空但正文却在夸能力？
10. **文档索引里所有和定价、额度、限额、配额、错误码相关的页面，是否逐个点开过？**（⚠️ 实测：索引打印出来了却没点，把已公开的信息写成了"官网未说明"）
11. **交付物里有没有"待测""建议自行试用"？**有就回去挖 YouTube 实测、深度评测、社区长帖，或改成判据
12. **口碑那一节有没有逐字引文？**只有我的总结、没有原文和来源 URL 的，不合格。三类（正面/负面/建议）是否都有？抽样标准写了吗？
13. **近 30 天变化写了吗？**每条有日期吗？（⚠️ 这一步漏过三轮）
14. **Wayback 定价页对比做了吗？**有没有"悄悄砍免费额度"这类信号？
15. **它自己的 /vs/ 页找过吗？**它认谁是威胁、回避哪个维度？
16. **条款正文读过吗？**责任限制、数据归属、SLA 赔付、涨价条款四项有没有？
17. **有没有因为"怕太长"而砍掉内容？**篇幅不是约束，砍掉的要加回来
18. **开篇有没有不含术语的 200 字摘要？**把它单独拿给一个不懂技术的人读，他能复述出三条结论吗？
19. **功能模块表有没有？**是业务语言还是 API 端点？（⚠️ 交端点清单等于没交）
20. **用户旅程有没有？**摩擦点是从引文取的还是我编的？
21. **界面截图 ≥3 张？**每张有没有说明支持哪条判断？**图是真的落盘并嵌进去了，还是只写了个链接？**（⚠️ 连续五轮为空，理由都是"环境做不到"，而一次都没试过）
21.1 **定价页是渲染后看过的吗？**下拉框、档位、月付/年付开关有没有逐个点过？（⚠️ 实测：静态抓取一个数字都没有，我写成"它不给价"，实际七档价格全在页面上）
21.2 **有没有哪句结论的措辞是"某页面上没有 X"？**逐条回去确认是渲染后确认的，不是抓取失败
21.3 **客户案例读了几个？**每个的数据是哪一年的？（⚠️ 实测：31 个案例只读 1 个，而那个的数据是七年前的）
21.4 **官方视频频道的标题列表过了吗？**（⚠️ 实测：一条 50 秒演示视频里有官网和文档都没提的 MCP 集成）
21.5 **产品在登录墙后就写"界面拿不到"了吗？**教学视频抽帧试过没有？
22. **相对市场位置有没有？**Tranco 趋势取了吗？口径与失真方向写了吗？（⚠️ 这一整块曾完全缺失）
23. **正文里还有多少取证过程？**状态码、接口名、探测细节应该在附录，不在正文
24. 通读一遍：这份报告读起来像不像一个专业顾问写的？有没有任何地方在为自己开脱？
